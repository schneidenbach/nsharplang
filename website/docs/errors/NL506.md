# NL506: a pattern that can never match

The arm is well-formed and the compiler can prove no value reaching it will ever satisfy it. NL506
is a "provably never" judgement, not a "probably not" one — everything N# models only partially is
admitted rather than reported.

```n#
func Describe(text: string): string {
    return match text {
        int n => n.ToString(),          // ERROR NL506
        _ => text
    }
}
```

```text
── [NL506] ERROR ───────────────────────────── Program.nl:3:9 ──

    3 |         int n => n.ToString(),          // ERROR NL506
      |         ^^^

This 'int' pattern can never match — a 'string' is never a 'int'
```

The span covers the pattern's type name. The message names both types in the order that makes the
proof readable: the scrutinee is a `string`, and a `string` is never an `int`.

## Why is this an error?

An arm that can never be taken is dead code with a claim attached. Somebody wrote it believing it
would run, so the honest reading is not "this is harmless" but "one of these two types is not what
you thought". Left in place it also silently changes the match's exhaustiveness, because an arm that
cannot match cannot cover anything either.

## How to fix it

Match the scrutinee with patterns its own type can satisfy:

```n#
func Describe(text: string): string {
    return match text {
        "" => "empty",
        _ => text
    }
}
```

If the arm was right and the scrutinee's type was too narrow, widen the scrutinee instead — a
parameter typed `object` genuinely can be an `int`, and NL506 is silent there.

## The same rule covers `is`

A type test in an ordinary expression asks exactly the same question and reports the same code, with
the wording turned around to suit a condition:

```n#
func Check(text: string): bool {
    return text is int          // ERROR NL506: this 'is int' check is always false
}
```

## When N# can prove it, and when it stays quiet

There are four ways for the answer to be "never", and they are the whole rule:

- two **value types** that are not the same type — `string` against `int` in the example, `int`
  against `double`;
- a value type tested against a **reference type** it is not assignable to;
- a reference tested against a **value type**;
- a **sealed** class tested against another class.

The last one is why an ordinary class hierarchy is silent. `Box` matched against an unrelated
`Crate` compiles without complaint, because some subclass of `Box` could implement or extend `Crate`
in a way the compiler cannot rule out. Seal `Box` and the same arm reports:

```n#
sealed class Box {
    Width: int
}

class Crate {
    Depth: int
}

func Describe(box: Box): string {
    return match box {
        Crate c => c.Depth.ToString(),          // ERROR NL506
        _ => box.Width.ToString()
    }
}
```

Anything the analyzer does not fully model is admitted **before** any negative reasoning starts, and
that list is deliberately generous: an unknown type, a type from a referenced assembly, a generic
type, an interface on either side, `object` on either side, a nullable on either side, and a union
on either side. A diagnostic that says "this can never match" has to be right every time, so partial
knowledge always resolves to silence.
