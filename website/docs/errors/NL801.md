# NL801: more than one base class

A class has **exactly one** base class, followed by any number of interfaces. That is not an N#
preference — it is a rule of the CLR, which N# compiles to, and no arrangement of the `:` clause
changes it.

```n#
class Timestamped {
    At: string
}

class Named {
    Name: string
}

class Event : Timestamped, Named {      // ERROR NL801
}
```

```text
── [NL801] ERROR ──────────────────────────── Program.nl:9:28 ──

    9 | class Event : Timestamped, Named {      // ERROR NL801
      |                            ^^^^^

'Event' declares more than one base class: 'Timestamped' and 'Named'

Suggestion: A class has exactly one base class, followed by any number of interfaces. Keep 'Timestamped' as the base and make 'Named' an `interface` that 'Event' implements, or hold one — give 'Event' a field `inner: Named`.
```

The report lands on the **second** base class — the first one is fine, and the second is the entry
that has to go.

## Why is this an error?

Single inheritance is what the runtime implements. A type's metadata has one base-class slot and
an arbitrarily long interface list, and there is nowhere for a second base to be written. Before
this check existed, N# accepted the declaration through analysis and the columnar backend refused
it later as [NL103](./NL103.md) — a message about the compiler's backend rather than about the
program.

## How to fix it

**Make one of them an interface.** This is usually what was meant: one of the two supplies
behaviour and the other only names a capability.

```n#
class Timestamped {
    At: string
}

interface Named {
    func Name(): string
}

class Event : Timestamped, Named {
    func Name(): string {
        return "event"
    }
}
```

**Or hold one instead of inheriting it.** Composition costs a field and works for any number of
participants:

```n#
class Timestamped {
    At: string
}

class Named {
    Name: string
}

class Event : Timestamped {
    named: Named
}
```

## The list is judged by kind, not by position

N# writes the base class and the interfaces in **one** `:` list, and the parser splits it by
position — the first entry becomes the base class and the rest become interfaces. That split is a
syntactic accident: whether an entry is a class or an interface is a question only name resolution
can answer, so NL801 resolves every entry and **counts the classes**.

Two consequences follow, and both are deliberate:

- `class Report : IPrintable, Document` names **one** base class, in an unusual position. It is
  silent.
- Any number of interfaces is always fine, in any position.

## What NL801 does not report

- **A `struct`, an `enum` or a delegate in the base list.** Those are a different fault with a
  different sentence.
- **An entry that did not resolve.** A count drawn from a name nobody could find would accuse a
  program whose real problem is [NL201](./NL201.md).
