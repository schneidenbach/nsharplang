# NL308: this member is not reachable from here

NL308 is the report for a member that **exists** and that you are **not allowed to read**. Two
independent rules can produce it, and the message tells you which one you hit:

- **the package rule** — a `camelCase` name is not exported from its namespace;
- **the declared rule** — a written `private`, `protected`, `private protected` or `internal` word
  keeps the member inside a type or a type family.

The first half of this page is the package rule; [the declared rule](#the-declared-rule) is below.

## The package rule

N# has two *default* visibility levels and you choose between them by **capitalisation**. A `PascalCase`
member is public — visible everywhere. A `camelCase` member is package-private: visible to every
file in its own namespace, and to nothing outside it. NL308 is what you get when code in another
package reads a `camelCase` member.

The rule is a *package* boundary, not a file boundary. Two files in the same namespace see each
other's `camelCase` members freely; this example needs two files because there is no other way to
have two packages.

```n#
// FILE Lib.nl
namespace Weather.Internals

class Station {
    Name: string
    readingCount: int

    constructor(name: string) {
        Name = name
        readingCount = 0
    }
}
```

```n#
// FILE Program.nl
namespace Weather.Report

import Weather.Internals

func Describe(station: Station): string {
    return station.Name + " " + station.readingCount.ToString()          // ERROR NL308
}
```

```text
── [NL308] ERROR ──────────────────────────── Program.nl:7:41 ──

    7 |     return station.Name + " " + station.readingCount.ToString()          // ERROR NL308
      |                                         ^^^^^^^^^^^^

'readingCount' is not exported from package/namespace 'Weather.Internals' — use PascalCase for cross-package visibility or keep camelCase members inside the declaring package
```

The message names the package the member belongs to, because that — not the file — is the boundary
that was crossed.

## Top-level declarations follow the same rule

`camelCase` is not only about class members. A top-level `func`, class, struct, record, enum, union
or type alias is namespace-private in exactly the same way — visible to every file that declares the
namespace, refused from any other:

```n#
// FILE Format.nl
namespace App.Ast

func formatTypeRef(t: TypeReference): string {
    return t.Name
}
```

```n#
// FILE Render.nl — same namespace, so this resolves with no import and no export
namespace App.Ast

func Render(t: TypeReference): string {
    return formatTypeRef(t)
}
```

```n#
// FILE Report.nl — a different namespace, so it does not
namespace App.Report

import App.Ast

func Report(t: TypeReference): string {
    return formatTypeRef(t)                                              // ERROR NL308
}
```

The `import` makes no difference: importing a namespace gives you its *exported* names, and
`formatTypeRef` is not one of them.

## Why is this an error?

Without a visibility rule, every field of every type is part of its public contract, and you find
out which parts callers depend on only when you try to change one. N# makes the choice a property
of the name so it is visible at the declaration and at every use: you can tell from
`station.readingCount` alone that you are reaching into something that was not offered to you.

Making it *capitalisation* rather than a `public` keyword is the same decision Go made, and it has
the same consequence — publishing a member is a rename, so it is a deliberate edit rather than a
one-word afterthought.

## How to fix it

**Export it**, if callers outside the package are meant to have it. Rename to PascalCase:

```n#
// FILE Lib.nl
namespace Weather.Internals

class Station {
    Name: string
    ReadingCount: int

    constructor(name: string) {
        Name = name
        ReadingCount = 0
    }
}
```

```n#
// FILE Program.nl
namespace Weather.Report

import Weather.Internals

func Describe(station: Station): string {
    return station.Name + " " + station.ReadingCount.ToString()
}
```

**Or offer a method instead**, if the field itself should stay internal — the usual answer when the
member is a representation detail rather than part of the idea:

```n#
// FILE Lib.nl
namespace Weather.Internals

class Station {
    Name: string
    readingCount: int

    constructor(name: string) {
        Name = name
        readingCount = 0
    }

    func Summary(): string {
        return Name + " " + readingCount.ToString()
    }
}
```

**Or move the caller into the package.** A file that declares `namespace Weather.Internals` is
inside the boundary and needs no change at either end.

## What the boundary is, exactly

- **The namespace, not the file.** A `camelCase` member is readable from any file that declares the
  same namespace. This is worth stating because the rule is often described as "file-private" —
  it is not.
- **The declaration's own name decides, unless a word overrides it.** With no accessibility word,
  the casing is the whole answer. A written `public` exports a `camelCase` member; a written
  `internal`, `private` or `protected` keeps a `PascalCase` one in. A member is never public in one
  place and private in another.
- **It applies to every member kind** — fields, properties and functions alike.
- **Top-level declarations follow the same rule**, and report the same code. A `camelCase`
  top-level `func` or type named from another namespace is NL308 at the reference, naming the
  namespace that owns it; from inside that namespace, any file may name it.

## The declared rule

N# also has the CLR's accessibility words, and they mean what they mean everywhere else on .NET:

| Written | Reachable from |
|---|---|
| *(nothing)* | the casing decides — see the package rule above |
| `public` | anywhere |
| `internal` | the assembly being compiled |
| `protected` | the declaring type and the types that derive from it |
| `protected internal` | either of the two above |
| `private protected` | a deriving type in the same project |
| `private` | the declaring type only |

`protected` has a **second half** that is easy to miss, and N# enforces it exactly as C# does
(§7.5.4): being inside a deriving type is not enough — the *receiver* has to be that type, or a type
derived from it.

```n#
namespace Demo

class Seeded {
    protected Seed: int = 3
}

class Grower: Seeded {
    func Mine(): int {
        return this.Seed                                                 // fine
    }

    func Sibling(other: Grower): int {
        return other.Seed                                                // fine
    }

    func Theirs(other: Seeded): int {
        return other.Seed                                                // ERROR NL308
    }
}
```

```text
── [NL308] ERROR ──────────────────────────── Program.nl:17:22 ──

   17 |         return other.Seed                                                // ERROR NL308
      |                      ^^^^

'Seed' is declared 'protected' on 'Seeded', so only 'Seeded' and the types that derive from it can reach it, through a receiver of the deriving type — this reads it from 'Grower'

Suggestion: Write the access inside a type that derives from 'Seeded' and read it through 'this' or a receiver of that derived type, or drop 'protected' from 'Seed'.
```

The refusal looks pedantic until you write the program it prevents: `other` is typed `Seeded`, so at
run time it may be some *other* type that derives from `Seeded`, and `Grower` has no business
reaching into that type's protected state.

`base.` is its own case and is always allowed inside a deriving type — `base.Seed` and
`base.Describe()` reach exactly what the base declared `protected`, which is what `base` is for.

### Free functions have no declaring type

A top-level `func` is not a member of any user type, so `private` on one cannot mean "this type
only". At namespace scope, `private` and `internal` both mean **package-private**, the same thing a
`camelCase` name means, and both emit CLR `Assembly` accessibility. See
[the language tour](../language-tour.md#visibility) for the whole table.
