# NL907: a nullable unwrap that can fail, or was not needed

NL907 is N#'s nullability advice at the two points where the type system and the code disagree about
whether a value is present: an unwrap that can fail, and an unwrap that was never needed. It is one
code because it is one question asked from both directions.

```n#
func Read(value: int?): int {
    return value.Value          // ERROR NL907
}
```

```text
── [NL907] ERROR ──────────────────────────── Program.nl:2:18 ──

    2 |     return value.Value          // ERROR NL907
      |                  ^^^^^

This '.Value' access can throw when the nullable value is absent

Suggestion: Prefer 'must value' for an explicit unwrap, or use 'match value { null => ..., inner => ... }' to handle both cases.
```

`.Value` on a nullable is a *silent* unwrap — it throws when the value is absent, and nothing in the
expression says so. The suggested `must value` does the same thing and says it, which is the whole
of the difference.

## Why is this an error?

`int?` means "possibly absent" and `.Value` means "give me the inner value now". Written together
they claim the absence cannot happen, without recording why. When that claim is wrong the failure is
an exception at run time, in a line that looks like a plain field read. N# asks for a spelling whose
risk is visible: `must` for a deliberate unwrap, or a `match` that handles both cases.

## How to fix it

Unwrap deliberately with `must`:

```n#
func Read(value: int?): int {
    return must value
}
```

Or handle the absent case, if there is a sensible answer for it:

```n#
func Read(value: int?): int {
    return value ?? 0
}
```

`must` is not a way to silence the compiler — it still throws when the value is absent. What it buys
is that the throw is now written down where a reader will see it.

## The same code from the other direction: a redundant `must`

NL907 also fires when the unwrap is not needed, because the value is already known to be present:

```n#
func Read(value: int): int {
    return must value          // ERROR NL907: this 'must' unwrap is redundant
}
```

reading `This 'must' unwrap is redundant — the expression is already known to be 'int'`.

This one catches a specific and common habit: adding `must` until the compiler stops complaining. It
also fires after **narrowing**, which is the case worth internalising — once a guard has proved the
value present, the `must` after it is redundant, not defensive:

```n#
func Make(width: int? = null): int {
    if width == null {
        return 0
    }

    return must width          // ERROR NL907 — the guard already narrowed `width`
}
```

The suggestion there is not just "delete the `must`". It also offers the better refactor: keep the
nullable value as it is and unwrap at the point where you actually need the inner value.

## NL905 or NL907

They divide cleanly, and the division is about what the compiler knows:

- [NL905](./NL905.md) is **flow-based**. It fires when a path reaches a use while the value is still
  maybe-null, and it goes away when you narrow.
- NL907 is about the **unwrap itself**, and narrowing is what turns one into the other. Guard a
  nullable and NL905 stops; leave the `must` behind and NL907 starts.

Seeing NL907 immediately after fixing an NL905 usually means the fix was applied twice.
