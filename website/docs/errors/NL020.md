# NL020: a declaration shadows an outer one

Declaring a name that an enclosing scope already binds is an error. N# does not allow shadowing: an
inner declaration would make the outer binding unreachable, so the same name would mean different
things depending on which brace a line sits inside. Renaming one of the two is always cheaper than
asking every reader to track that.

```n#
func Describe(compact: bool): string {
    label := () => "the verbose label"
    if compact {
        label := () => "short"          // ERROR NL020
        return label()
    }

    return label()
}
```

```text
── [NL020] ERROR ───────────────────────────── Program.nl:4:9 ──

    4 |         label := () => "short"          // ERROR NL020
      |         ^^^^^

Variable 'label' shadows another 'label' from an outer scope — this can lead to confusing bugs

Suggestion: Consider renaming to avoid confusion with the outer 'label'
```

The span is the inner declaration — the one that took the name — and the suggestion notes that the
outer binding is still in scope, which is the fact that makes renaming the inner one safe.

## Why is this an error?

Shadowing bugs do not look like bugs. The code compiles, the name resolves, and the value is simply
the wrong one; the only evidence is a brace several lines up. They are also asymmetric in the worst
way: deleting the inner declaration during a later edit silently redirects every use to the outer
binding, so the mistake can be *introduced* by removing a line.

N# takes the position that this is not a style preference. A language with shadowing has to teach
every reader to track scope depth while reading; a language without it lets a name mean one thing
per function. The cost is a rename, paid once, at the point where the ambiguity was created.

## How to fix it

Give the inner binding its own name — or, if you meant to update the outer one, assign to it instead
of declaring a second one:

```n#
func Describe(compact: bool): string {
    label := () => "the verbose label"
    if compact {
        shortLabel := () => "short"
        return shortLabel()
    }

    return label()
}
```

## Which code reports this, and which reports NL316

Most shadowing in N# is caught earlier, by the analyzer, as [NL316](./NL316.md) — "'x' shadows an existing 'x'
from an enclosing scope". That check covers *value* bindings, and it is the diagnostic you will see
for an ordinary shadowed local:

```n#
func Sum(values: int[]): int {
    total := 0
    for value in values {
        total := value          // reported as NL316, not NL020
        total = total + 1
    }

    return total
}
```

NL020 is the linter's rule for the same mistake, and it is what remains where NL316's value-binding
filter does not apply — most visibly a local that holds a function, as in the example at the top of
this page. The two messages describe the same problem; the fix is identical either way, and neither
one is a weaker version of the other.

## What counts as an enclosing binding

- **Every enclosing scope, not just the nearest one.** A name bound two blocks out still shadows.
- **Parameters count.** A local declared inside `Shadow(label: string)` that is also called `label`
  is reported.
- **`_` and every `_`-prefixed name are exempt.** Renaming the inner binding `_label` silences the
  rule, on the grounds that a name marked deliberately uninteresting is not one anybody will confuse.
- **Redeclaring in the *same* scope is a different mistake** and gets a different code ([NL306](./NL306.md)) —
  this rule is only about an inner scope taking an outer name.
