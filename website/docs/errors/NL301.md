# NL301: variable not found

A bare name in an expression has to resolve to something N# can see from where you wrote it: a
local or parameter in scope, a member of the enclosing type, a built-in type name, or a top-level
declaration exported by some file in the project. NL301 is the answer when none of those channels
knows the name.

```n#
func Total(price: int, taxRate: int): int {
    subtotal := price * taxRate
    return subtotal + taxRat          // ERROR NL301
}
```

```text
── [NL301] ERROR ──────────────────────────── Program.nl:3:23 ──

    3 |     return subtotal + taxRat          // ERROR NL301
      |                       ^^^^^^

Variable 'taxRat' not found

I cannot find a `taxRat` variable on line 3:

Hint: Variables need to be declared before they can be used. If you meant to
use a variable from outside this function, make sure it's in scope.

Suggestion: taxRate
```

The last line is the one that usually ends the investigation. N# scores every name in scope against
the one you wrote, and when something is close enough it names it outright — here `taxRate`, one
character away from what was typed.

## Why is this an error?

There is no fallback that would make this safe. N# has no implicit globals and no late-bound name
lookup, so a name that resolves to nothing at compile time would resolve to nothing at run time
either. Reporting it here — with the position of the name itself underlined, not the whole
expression — is the earliest and cheapest place to say so.

## How to fix it

Use the name that exists, or declare the one you meant:

```n#
func Total(price: int, taxRate: int): int {
    subtotal := price * taxRate
    return subtotal + taxRate
}
```

## Which code an unresolved name gets

N# splits "I cannot find this name" across several codes, because the fix differs by position. If
you are looking for the rule that applies to your line, find the position first:

- an ordinary expression position — **NL301**, this code;
- a callee position, `Compute()` — [NL412](./NL412.md), which suggests callable names rather than variables;
- a type position — an annotation, a `new`, a generic argument — [NL201](./NL201.md);
- after a dot, `user.Nme` — [NL303](./NL303.md), which knows the receiver's type and can list its
  members;
- a name that a *different* package in the project declares but does not export — `NL308`. That one
  is a visibility failure rather than a lookup failure, and it says so.

A dotted name whose **root** does not resolve is NL301 on the root: `Persn.Count()` reports
`Variable 'Persn' not found`, because N# resolved as far as the first segment and got nothing.
