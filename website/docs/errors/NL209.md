# NL209: a name two imports both supply

A file's imports each bring a set of names into scope. When two of them bring in the *same*
name, nothing about the file says which one you meant — and whichever `import` you happened to
write first is not an answer. NL209 is the report for that tie, and it names both candidates in
full so you can write the one you mean.

```n#
// FILE Reporting.nl
namespace Reporting

class Widget {
    static func Render(): string {
        return "report"
    }
}
```

```n#
// FILE Dashboard.nl
namespace Dashboard

class Widget {
    static func Render(): string {
        return "dashboard"
    }
}
```

```n#
// FILE Program.nl
namespace App

import Reporting
import Dashboard

func Show(): string {
    return Widget.Render()          // ERROR NL209
}
```

```text
── [NL209] ERROR ──────────────────────────── Program.nl:8:12 ──

    8 |     return Widget.Render()          // ERROR NL209
      |            ^^^^^^

'Widget' is ambiguous between 'Reporting.Widget' and 'Dashboard.Widget'

`Widget` could mean either of two types on line 8, and both are in scope here:

`Reporting.Widget` and `Dashboard.Widget` are brought in by different imports,
so neither one is closer than the other. A type declared in this file's own namespace
would win outright; two imports tie.

Suggestion: Write the one you mean in full — 'Reporting.Widget' — or remove the import that supplies the other.

See: https://schneidenbach.github.io/nsharplang/docs/errors/NL209
```

## How to fix it

**Qualify the reference.** This is almost always what you want, because it says what you mean
at the place the reader is looking:

```n#
namespace App

import Reporting
import Dashboard

func Show(): string {
    return Reporting.Widget.Render()
}
```

**Or drop the import you do not need.** If the file only ever wanted one of the two namespaces,
removing the other import removes the tie — and [NL010](./NL010.md) will tell you when an import
has stopped being used.

## What is *not* ambiguous

**A type in this file's own namespace wins outright.** A closer declaration is not a tie, so a
`Widget` declared in `namespace App` is what `Widget` means in that file, whatever the imports
bring in. This is the same rule C# applies to `using` directives.

**A type in an *enclosing* namespace wins outright too.** A file in `App.Models.Internal` sits
inside `App.Models`, inside `App`, inside the global namespace, and an exported declaration in any
of them is nearer than anything the file imported — so it wins, in that order, with nothing to
report:

```n#
// FILE Shared.nl
namespace App

class Widget {
    static func Render(): string {
        return "shared"
    }
}
```

```n#
// FILE Program.nl
namespace App.Models

import Reporting

func Show(): string {
    return Widget.Render()          // App.Widget — the enclosing namespace is nearer
}
```

Importing an enclosing namespace changes nothing: it was already in scope, so the import is
redundant rather than a second candidate that could tie.

A **sibling** namespace is a different matter. `App.Ast` neither contains nor is contained by
`App.Columnar`, so it is not nearer to anything — it reaches a file only through an `import`, and
then it ties with any other import that supplies the name, exactly as above.

**Auto-discovery is never a candidate.** N# lets a file use an exported type from another
namespace in the same project without importing it — but that is the channel that runs when *no*
import supplies the name, so it can never tie with one. An explicitly imported type always wins
over an auto-discovered one, and that precedence is itself a fix: a source type in an unrelated
namespace no longer shadows a CLR type your `import` brought in.

**A qualified spelling is never ambiguous.** `Reporting.Widget` names one declaration, so it is
unaffected by however many other namespaces declare a `Widget`. You do not have to write the whole
path: the leftmost segment of a qualified name is looked up by the same outward climb, so from
inside `App` the spelling `Ast.Widget` already names `App.Ast.Widget`.

## Free functions tie the same way

A top-level `func` is reached from another namespace through an `import` and nothing else — there is
no auto-discovery tier for functions — so two imports that each export the same function name is the
same tie:

```n#
// FILE reporting.nl
namespace Reporting

func Render(): string {
    return "report"
}
```

```n#
// FILE dashboard.nl
namespace Dashboard

func Render(): string {
    return "dashboard"
}
```

```n#
// FILE Program.nl
namespace App

import Reporting
import Dashboard

func Show(): string {
    return Render()                 // ERROR NL209
}
```

The exclusions are the same: a function declared in **this file**, or an exported one in this file's
own or any **enclosing** namespace, is nearer than any import and wins outright. What differs is the
fix — a free function has no namespace-qualified call spelling, so **drop the import you do not
mean**, or move the function you want into a namespace this file already sits in.

## A referenced assembly's type ties the same way

Nothing about the rule depends on where the two declarations live. A source declaration ties with a
referenced assembly's type, and two *imported CLR namespaces* that declare one spelling tie with each
other, exactly as two source namespaces do:

```n#
// FILE Reporting.nl
namespace Reporting

class Range {
    func Describe(): string {
        return "reporting"
    }
}
```

```n#
// FILE Program.nl
namespace App

import System
import Reporting

func Show(span: Range): string {      // ERROR NL209
    return span.Describe()
}
```

```text
'Range' is ambiguous between 'Reporting.Range' and 'System.Range'
```

Write `Reporting.Range` or `System.Range` in full, or drop the import you do not need. The same
report answers `import System` beside a library namespace that declares its own `Range`, where
neither candidate is yours.

This used to be silent. The tie was checked against your own sources and, only then, against
metadata — so two imports whose types both come from assemblies resolved to whichever import you had
written first, and a program could mean a type its author never chose.

## Every position a name is written in

`Widget` is one name wherever it appears, so the tie is reported wherever it is written: a type
annotation, a `new`, a type argument, a `typeof`, an `is` or `as`, a static receiver
(`Widget.Create()`), and an attribute's brackets. `[Tag]` is a type reference wearing brackets, and
because it may legally mean either `Tag` or `TagAttribute`, the tie is reported for whichever of the
two spellings actually collides.
