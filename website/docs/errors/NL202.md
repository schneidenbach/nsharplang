# NL202: a value of one type is used where another is required

NL202 is the most common diagnostic in N#: a value of one type appears where a value of another
is required. Every position in the language that has an expected type reports through this one
code — annotations, assignments, returns, arguments, initializer members, conditions, array
elements, match arms. The message always names both types, and it always names the position by
construct, so the first line tells you which rule you hit before you read a single type.

```n#
class Order {
    Total: int
}

func Describe(order: Order): string {
    label: string = order.Total          // ERROR NL202
    return label
}
```

```text
── [NL202] ERROR ──────────────────────────── Program.nl:6:21 ──

    6 |     label: string = order.Total          // ERROR NL202
      |                     ^^^^^^^^^^^

Variable 'label' is typed as 'string', but the value is 'int'

I am having trouble with this code on line 6:

Expected: `string`
  Actual: `int`

Hint: You can convert an integer to a string using .ToString() or string
interpolation: $"{yourNumber}"
```

Read the `Expected` / `Actual` pair first: `Expected` is what the position demands, `Actual` is
what you wrote. The hint underneath is chosen from that pair of types rather than from the
position, so the same advice about `int.Parse` appears whether the `string` was in a return, an
argument or an initializer.

## Why is this an error?

N# is statically typed for the CLR, and a slot that holds an `int` holds four bytes of integer —
there is nowhere in it for a `string` reference to go. N# does insert widening conversions where
one exists and cannot lose anything (see below), but there is no such conversion here. Inventing
one — parsing the text, or printing the number — would be a guess about intent, and a wrong
guess would move the surprise from compile time to run time, landing somewhere other than the
line that caused it.

## How to fix it

Convert explicitly, or change the annotation to the type you actually have. Here the value is a
number and the variable wanted text, so the conversion belongs at the value:

```n#
class Order {
    Total: int
}

func Describe(order: Order): string {
    label := order.Total.ToString()
    return label
}
```

## Every position that reports NL202

The code is the same in all of them; only the first line of the message changes, and it always
names the position by construct. These are the positions, each with the sentence N# actually
prints:

**A declaration with an annotation** — the value must be assignable to the written type.

```text
Variable 'label' is typed as 'string', but the value is 'int'
```

**An assignment to something already declared** — the value must be assignable to the target.

```text
Type mismatch in assignment — expected 'int' but got 'string'
```

**A return** — the value must be assignable to the function's return type.

```text
Function 'Length' should return int but returns string
```

**A call argument** — the argument must be assignable to the parameter. The message names the
parameter and the argument's position in the call.

```text
Cannot pass `string` as argument for parameter `n` of type `int`

Argument 1 in the call to `Twice` has the wrong type:
```

**An object-initializer member** — `new Order { Total: "ten" }` checks each member against the
member's declared type.

```text
'Total' is typed as 'int', but the value is 'string'
```

**A condition** — `if` and `while` both require `bool`, and each names its own construct. N#
does not treat a non-zero number or a non-null reference as true.

```text
The condition in an 'if' must be a boolean, but I found 'int'
The condition in a 'while' loop must be a boolean, but I found 'int'
```

**An array literal's elements** — the first element fixes the type and every later element is
checked against it, so the caret lands on the first element that disagrees rather than on the
whole literal.

```text
All elements in an array must be the same type — the first element is 'int' but I found 'string'
```

**A `match` arm** — likewise, the first arm fixes the result type.

```text
All match arms must return the same type — the first arm returns 'int', but this arm returns 'string'
```

**A void call used as a value** — a function with no return type produces nothing, so there is
nothing to store.

```text
This expression doesn't return a value (it's void) — you can't assign it to a variable
```

Most of these also print the `Expected` / `Actual` pair underneath. The array-element,
match-arm, `while`-condition and void-call reports do not — their single sentence already
carries both types — and they end with a short generic suggestion instead.

## What N# accepts without a word

NL202 is an assignability check, not an identity check, so several pairs that look mismatched
are fine and report nothing at all:

- **widening between numeric types** — an `int` returned from a function declared `: long`
  compiles, and so does `total: long = 5`;
- **an integer literal in a floating-point position** — `func Go(): double { return 3 }` is
  clean;
- **`null` into a reference type** — `Name: string = null` is accepted. N# embraces .NET's null
  rather than pretending it does not exist, so this is not where null is policed.

What is *not* accepted is anything with a bit pattern to reinterpret: `v: bool = 1` reports
NL202, because a number is not a truth value in N# any more than in the CLR.

## Nullable and non-nullable are different types

`string?` and `string` are two types, and using one where the other is required is an ordinary
NL202 with its own hint:

```text
Function 'Go' should return string but returns string?

Expected: `string`
  Actual: `string?`

Hint: You're trying to use a nullable value where a non-nullable is expected.
You need to handle the null case, perhaps with 'if (x != null)' or the
null-coalescing operator 'x ?? defaultValue'.
```

The `?` in the `Actual` line is the whole difference. If the two types look identical in the
message, look again for it before looking anywhere else.

## When NL202 is a consequence, not a cause

Two shapes produce an NL202 that will disappear on its own once the real mistake is fixed, and
both are worth recognising so you do not chase them:

- **an unresolved return type.** [NL201](./NL201.md) on the annotation is followed by an NL202
  on every `return`, because the return check runs against a type that was never found.
- **a generic used without its type arguments.** [NL207](./NL207.md) on `new Pair { ... }` is
  followed by an NL202 per initializer member, each one comparing your value against the bare
  type parameter: `'First' is typed as 'A', but the value is 'int'`. A message whose `Expected`
  is a single capital letter is nearly always this.

In both cases the NL202 is downstream of the real fault. Fix the first diagnostic in the file
and recompile before reading the rest.
