# NL006: this code can never run

Code placed after a `return` or a `throw` in the same block can never execute. The linter reports
it as NL006, and it blocks the build.

```n#
func Classify(): string {
    return "positive"
    return "unreachable"          // ERROR NL006, NL312
}
```

```text
── [NL312] ERROR ───────────────────────────── Program.nl:3:5 ──

    3 |     return "unreachable"          // ERROR NL006, NL312
      |     ^^^^^^

This code will never run — there's a 'return' or 'throw' above it

Suggestion: Remove unreachable code or restructure control flow

── [NL006] ERROR ───────────────────────────── Program.nl:3:5 ──

    3 |     return "unreachable"          // ERROR NL006, NL312
      |     ^^^^^^

This code will never run — there's a 'return' or 'throw' above it

Suggestion: Remove the unreachable code, or move it before the return/throw if it should execute
```

## Two codes, one mistake

Notice that the same line is reported **twice** — once as NL006 and once as `NL312`. That is not a
bug in the example; it is what this shape does today, and the page marks both because a page must
say what actually happens.

Two owners reach the same conclusion by different routes. `NL312` is the semantic analyzer's
finding, from the same control-flow analysis that decides whether a function returns on every path.
NL006 is the linter's, from its own simpler walk. The linter's test for "this statement ends the
block" accepts a strict *subset* of the shapes the analyzer accepts, so every NL006 arrives beside
an `NL312` — while `NL312` appears alone for the shapes only the analyzer understands, such as an
`if`/`else` where both branches return.

The practical consequence: **fixing the code clears both**, and there is never a case where you
must satisfy them separately.

## Why is this an error?

Unreachable code is a statement about intent that the compiler can prove false. Either the code was
meant to run — in which case the control flow above it is wrong — or it is dead, in which case it
is a comment that looks like logic and will mislead the next reader. Neither is something to leave
in a build.

N# is near-zero-warnings: there is no ignorable tier for this. A warning about dead code is one you
scroll past.

## How to fix it

Delete it, or move it above the `return`:

```n#
func Classify(): string {
    return "positive"
}
```

## What counts as unreachable

- a statement after `return` or `throw` **in the same block**;
- a statement after a `break` or `continue` in the same block.

And what does not:

- a statement after an `if` whose branches all return — reachable as far as the linter is
  concerned, and reported by `NL312` alone;
- the code after a loop that happens never to terminate. N# does not attempt to prove
  non-termination, and a rule that guessed would be worse than one that stays quiet.
