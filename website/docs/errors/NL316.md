# NL316: a declaration shadows an enclosing one

A local or parameter may not reuse a name that an enclosing scope already bound. N# has no shadowing:
inside a function, one name means one thing from its declaration to the end of the block that
declared it. Redeclaring it in a nested block is NL316, and it is a hard error rather than a lint.

```n#
func Describe(count: int): string {
    if count > 10 {
        count := 10          // ERROR NL316
        return $"{count} items"
    }

    return $"{count} items"
}
```

The underline is on the **name being declared**, not on the `:=`. That is the token you rename — or
delete, if what you meant was an assignment.

```text
── [NL316] ERROR ───────────────────────────── Program.nl:3:9 ──

    3 |         count := 10          // ERROR NL316
      |         ^^^^^

'count' shadows an existing 'count' from an enclosing scope — N# forbids shadowing because it hides the outer binding and invites confusing bugs

Suggestion: Rename this declaration (the outer 'count' is still in scope), or remove it and reuse the existing 'count'
```

## Why is this an error?

The example above is the reason. `count := 10` looks like it clamps the parameter, and it does not:
it introduces a second `count` that lives until the `if` block ends, leaves the parameter untouched,
and makes the two `return` statements — which read identically — return different things. One
character separates the code that works from the code that does not, and nothing about the shape of
the program tells you which one you wrote.

Shadowing also makes every later edit riskier than it looks. Deleting the inner declaration silently
repoints every use in the block at the outer binding, with no diagnostic, because both spellings are
legal.

## How to fix it

If you meant to change the existing binding, assign to it:

```n#
func Describe(count: int): string {
    if count > 10 {
        count = 10
        return $"{count} items"
    }

    return $"{count} items"
}
```

If you meant a new value, give it a new name:

```n#
func Describe(count: int): string {
    if count > 10 {
        capped := 10
        return $"{capped} items"
    }

    return $"{count} items"
}
```

## What is not shadowing

**A local may share a name with a field or property.** Class members and locals live in different
scopes, and a method that writes `count := 5` alongside a field named `count` is accepted:

```n#
class Counter {
    count: int

    func Bump(): int {
        count := 5
        return count
    }
}
```

**Sibling blocks are not nested.** Two blocks that follow one another can each declare `text`,
because neither is inside the other and the first name is out of scope before the second appears:

```n#
func Describe(flag: bool): string {
    if flag {
        text := "yes"
        return text
    }

    if !flag {
        text := "no"
        return text
    }

    return ""
}
```

The rule is about *enclosing* scopes, not about a name appearing twice in a file.

## One diagnostic, not two

N# also ships a linter rule for shadowed variables, [NL020](./NL020.md). When the compiler's NL316 fires, the
linter rule is suppressed for that file, so a single shadowing mistake produces a single diagnostic
rather than a matched pair saying the same thing in two voices.
