# NL330: a loop variable annotated with a type its elements cannot become

A `for` loop's variable may carry a written type — `for m: Match in matches` — and each element is
then converted to that type once per iteration. The conversion is the one a **cast** performs: a
downcast, an unboxing, a numeric conversion, or any of the conversions an assignment already makes.
NL330 reports the loop where **no** conversion exists in either direction, so no element of the
collection could ever take the annotated type.

```n#
func TotalLength(values: List<int>): int {
    total := 0
    for s: string in values {        // ERROR NL330
        total = total + s.Length
    }
    return total
}
```

```text
── [NL330] ERROR ──────────────────────────────── Program.nl:3:12 ──

    3 |     for s: string in values {        // ERROR NL330
      |            ^^^^^^

A 'int' cannot be read as a 'string'

This loop hands `s` one `int` at a time, and `string` is not a type any `int` can be
converted to:

Hint: An annotated loop variable converts each element the way a cast does — a downcast, an
unboxing, or a numeric conversion. There is no conversion between `int` and `string` in
either direction, so no element could ever take that type.

Suggestion: Annotate `s` with `int` or a type it converts to, drop the annotation and let the
element type be inferred, or iterate a collection whose elements are `string`.
```

## How to fix it

**Drop the annotation.** The element type is inferred from the collection, which is what most loops
want.

```n#
for value in values {
    total = total + value
}
```

**Or annotate with a type the element really converts to.** A widening is always available between
the numeric types, so `for n: long in values` over a `List<int>` is fine.

```n#
for n: long in values {
    total = total + n
}
```

**Or iterate a collection whose elements are that type.** If `string` is what the body needs, produce
strings.

```n#
for s: string in values.Select(v => v.ToString()) {
    total = total + s.Length
}
```

## What the annotation is for

The annotation exists so that a sequence typed by an interface *older* or *wider* than its contents
can be read at the type its elements actually have. The conversion is deliberately a cast, not an
assignment, so all four of these compile:

```n#
for m: Match in Regex.Matches(text, "a") { }   // MatchCollection's elements are `object`
for v: int in objects { }                      // an unboxing, from List<object>
for n: long in numbers { }                     // a numeric widening, from int[]
for s: string in legacy { }                    // ArrayList's elements are `object`
```

Because it is a cast, the check is a **compile-time** one about whether the conversion could ever
apply — not a promise that every element will satisfy it. An element that is the wrong runtime type
throws `InvalidCastException` at the loop, exactly as the equivalent cast would.

## Where the rule applies

- It applies to any `for … in` with a written loop-variable type, however the collection is
  enumerated — an array, a `string`, a `Span<T>`, a sequence interface, or a user type carrying the
  `GetEnumerator` pattern.
- It is **silent** when either type is unknown: a collection that is not enumerable has already
  reported [`NL202`](./NL202.md), and repeating the complaint about the element type it could not
  produce would name types you cannot act on.
- The annotated type is what the loop variable *is* for the rest of the loop — hover, completion and
  the body's own type checking all read it — whether or not the conversion was accepted, so a
  refused annotation produces one diagnostic rather than a cascade through the body.
