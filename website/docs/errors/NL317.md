# NL317: a .NET event used without on or off

A .NET event is not a field, and N# does not let you treat it as one. `+=`, `-=`, `=` and reading the
event as a value are all rejected: an event is reached through the `on` and `off` keywords, and
through nothing else.

```n#
import System

func Watch(handler: ConsoleCancelEventHandler) {
    Console.CancelKeyPress += handler          // ERROR NL317
}
```

The underline covers the whole receiver-and-event path, and the suggestion is written against the
event you actually named — it is a template you can paste over the line.

```text
── [NL317] ERROR ───────────────────────────── Program.nl:4:5 ──

    4 |     Console.CancelKeyPress += handler          // ERROR NL317
      |     ^^^^^^^^^^^^^^^^^^^^^^

'CancelKeyPress' is a .NET event — it can't be subscribed to with '+='

Suggestion: Subscribe with `on Console.CancelKeyPress (sender, args) => { ... }`; it returns a subscription you can later pass to `off`.
```

## Why is this an error?

C#'s `+=` and `-=` on an event work by *value equality of delegates*, and that is where the classic
leak comes from: to unsubscribe you must reconstruct a delegate equal to the one you added. Anyone
who has written `x.Changed += (s, e) => Redraw()` and then tried to detach it knows the shape of that
bug — the lambda is a new object every time, so the `-=` matches nothing and silently does nothing.

N# closes the hole by making subscription an *expression*. `on` returns a subscription handle, `off`
takes it back, and detaching never depends on reproducing a delegate:

```n#
sub := on button.Clicked (sender, args) => { }
off sub
```

Because the handle is the only way to unsubscribe, there is no useful meaning left for `+=` on an
event — so rather than accept it and quietly diverge from what `off` can undo, N# reports it.

## How to fix it

Replace the assignment with `on`, and keep the handle if you will ever need to detach:

```n#
import System

func Watch() {
    sub := on Console.CancelKeyPress (sender, args) => { }
    off sub
}
```

## Every form NL317 covers

All of these are the same diagnostic, with a sentence tuned to what you wrote:

```n#
Console.CancelKeyPress += handler     // 'CancelKeyPress' is a .NET event — it can't be
                                      //  subscribed to with '+='

Console.CancelKeyPress -= handler     // 'CancelKeyPress' is a .NET event — it can't be
                                      //  unsubscribed with '-='

Console.CancelKeyPress = handler      // 'CancelKeyPress' is a .NET event — it can't be
                                      //  assigned with '='

return Console.CancelKeyPress         // 'CancelKeyPress' is a .NET event and can only be
                                      //  used with `on`/`off`

off Console.CancelKeyPress            // same sentence — `off` takes the subscription that
                                      //  `on` returned, never the event itself
```

That last one is worth its own note: naming the event after `off` is **NL317**, not
[NL318](./NL318.md). You are still using the event as a value; you have only moved where.

## What `on` and `off` compile to

The `on`/`off` form this diagnostic asks you to write compiles end to end: `on` calls the event's own
`add` accessor and hands you a handle that remembers the exact delegate it added, and `off` calls the
`remove` accessor through that handle. The receiver is any expression that owns the event — a static
type, a local, a parameter, a field, `this.`, a property chain, an indexed element — and the handler
is a lambda, a delegate value, or a function named directly.

Detaching twice is a no-op, and two subscriptions to one event detach independently, which is the
thing `-=` cannot do for an inline lambda. See
[the language tour](../language-tour.md#subscribing-to-net-events) for the full set of forms.
