# NL505: a match guard that is not a boolean

A `when` clause decides whether an arm applies, so it has to answer yes or no. N# requires a `bool`
and does not accept anything else as a stand-in — no truthiness, no implicit conversion from a
number or a reference.

```n#
func Describe(value: int): string {
    return match value {
        n when n % 2 => "odd",          // ERROR NL505
        _ => "even"
    }
}
```

```text
── [NL505] ERROR ──────────────────────────── Program.nl:3:18 ──

    3 |         n when n % 2 => "odd",          // ERROR NL505
      |                  ^

A match guard must be a boolean, but this expression is 'int'

Suggestion: Guard expression must be boolean type
```

The type in the message is what the guard expression actually evaluates to. Here `n % 2` is an
`int`, which is the shape of the mistake: the remainder was meant to be compared, not tested.

## Why is this an error?

Truthiness is where a whole family of bugs lives. `n % 2` is truthy for every odd number in C and
falsy for every even one, so the arm would appear to work — until the same habit is applied to a
value where zero is meaningful, or to a reference where "not null" was never the question. N# has
one boolean type and one way to get one, and asking for it explicitly costs three characters.

## How to fix it

Compare, and let the comparison produce the `bool`:

```n#
func Describe(value: int): string {
    return match value {
        n when n % 2 == 1 => "odd",
        _ => "even"
    }
}
```

## Guards are not patterns

The two halves of an arm do different jobs and the compiler treats them differently. The pattern
before `when` is matched structurally; the guard after it is an **ordinary expression**, analysed in
a scope where the pattern's bindings are already in place. That is why `n` is usable in the guard,
and why everything you know about expressions applies there — including that `&&`, `||` and `!`
require `bool` operands of their own.

## A guarded arm never proves coverage

This is the interaction that surprises people. Because a guard may be false at run time,
exhaustiveness checking skips guarded arms entirely: an arm `Shape.Circle { radius: r } when r > 0.0`
leaves `Circle` uncovered, and the match still reports [NL501](./NL501.md). A guard narrows *which*
values an arm accepts; it never tells the compiler that a case is handled.

The practical consequence is to follow a guarded arm with an unguarded one for the same case, rather
than relying on the guard being total.
