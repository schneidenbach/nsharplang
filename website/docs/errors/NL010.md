# NL010: an import that nothing in the file uses

An import no code in the file uses is an error. Imports are the file's declared dependency list, and
a list naming things the file does not touch is worse than no list: it survives every refactor that
removed the last real use, and after a few of those nobody can tell which lines still mean
something. There is no `_` opt-out here — the fix is to delete the line.

```n#
import System.Text          // ERROR NL010

func Double(value: int): int {
    return value * 2
}
```

```text
── [NL010] ERROR ───────────────────────────── Program.nl:1:8 ──

    1 | import System.Text          // ERROR NL010
      |        ^^^^^^^^^^^

The import 'import System.Text' is not used by any code in this file

Suggestion: Remove 'import System.Text' to keep your imports clean
```

The span covers the namespace rather than the `import` keyword, and the rule is per file: another
file in the same project importing `System.Text` has no bearing on this one.

## Why is this an error?

The import block is the one place a reader can look to answer "what does this file depend on".
Stale lines are the default outcome of ordinary work — you delete the last `StringBuilder` in a file
and nothing tells you the import is now dead — so without a build-blocking rule the block decays
into noise that nobody trusts and therefore nobody maintains.

It also keeps the block usable as a review signal. A diff that adds an import is a diff that added a
dependency, which is worth a second of attention. That only holds if imports leave as reliably as
they arrive.

## What counts as a use

Any mention of a name the import could supply. The rule is deliberately generous, because a false
NL010 deletes a line the code needs:

- a **type written anywhere in a signature or declaration** — a parameter type, a return type, a
  field's type, a local's annotation — including inside type arguments, so
  `Dictionary<string, StringBuilder>` uses both namespaces;
- a **constructed type**: `new StringBuilder()`;
- a **`typeof` operand**: `typeof(DateTime)` keeps `import System` alive;
- a **member name that resolves to an extension method** the import supplies: `values.Where(…)`
  keeps `import System.Linq` alive;
- an **identifier inside an interpolated string hole**: `$"{DateTime.Now}"` is enough on its own;
- a **type named in a pattern, an `is`, an `as`, a cast or a `catch` clause**: `o is StringBuilder`,
  `match o { StringBuilder sb => … }` and `catch (error: InvalidOperationException)` all count.

The last of those was the rule's blind spot until it was closed. A file whose only mention of
`System` was the exception type of a `catch` clause reported NL010 against an import it needed — an
error that stops the build on correct source, and whose `nlc fix` deletes the line. This file is
clean:

```n#
import System

func Try(): int {
    try {
        return 1
    } catch (error: InvalidOperationException) {
        return 0
    }
}
```

The same slot now also asks the opposite question: a `catch` clause naming a type with no import
reports [NL002](./NL002.md) under the type name, exactly as an `is` or a pattern does.
