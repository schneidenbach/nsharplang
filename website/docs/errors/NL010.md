# NL010: an import that nothing in the file uses

An import no code in the file uses is an error. Imports are the file's declared dependency list, and
a list naming things the file does not touch is worse than no list: it survives every refactor that
removed the last real use, and after a few of those nobody can tell which lines still mean
something. There is no `_` opt-out here — the fix is to delete the line.

```n#
import System.Text          // ERROR NL010

func Double(value: int): int {
    return value * 2
}
```

```text
── [NL010] ERROR ───────────────────────────── Program.nl:1:8 ──

    1 | import System.Text          // ERROR NL010
      |        ^^^^^^^^^^^

The import 'import System.Text' is not used by any code in this file

Suggestion: Remove 'import System.Text' to keep your imports clean
```

The span covers the namespace rather than the `import` keyword, and the rule is per file: another
file in the same project importing `System.Text` has no bearing on this one.

## Why is this an error?

The import block is the one place a reader can look to answer "what does this file depend on".
Stale lines are the default outcome of ordinary work — you delete the last `StringBuilder` in a file
and nothing tells you the import is now dead — so without a build-blocking rule the block decays
into noise that nobody trusts and therefore nobody maintains.

It also keeps the block usable as a review signal. A diff that adds an import is a diff that added a
dependency, which is worth a second of attention. That only holds if imports leave as reliably as
they arrive.

## What counts as a use

**Whatever the file BOUND through it.** The rule does not read your source looking for names it
recognises — it reads what the analyzer *resolved*. When a simple name resolves, the namespace that
supplied it is known exactly: it is the prefix that, together with the spelling you wrote, spells the
resolved type's full name.

```text
    List                    ->  System.Collections.Generic.List`1   ->  System.Collections.Generic
    Collections.Generic.List (with `import System`)
                            ->  System.Collections.Generic.List`1   ->  System
    System.Type             ->  System.Type                         ->  nothing: fully qualified
```

An import is used when it appears among those, and dead when it does not. So the list of positions
that count is not a list at all — it is every position where a name can resolve:

- a **type written anywhere**: a parameter, a return, a field, a local annotation, a base class, an
  implemented interface, a generic constraint, a union case payload, a type alias target, a newtype's
  underlying type, an indexer's element and parameter types;
- **inside** a written type: a type argument, a tuple element, a function type's parameters, so
  `Dictionary<string, StringBuilder>` uses both namespaces and `new List<StringBuilder>()` does too;
- a **constructed type**, a **`typeof` operand**, and a type named by a **pattern**, an **`is`**, an
  **`as`**, a **cast** or a **`catch` clause**;
- a **static receiver** — `Console.WriteLine(…)` and `Math.Sqrt(…)` keep `import System` alive
  though the file writes no annotation at all;
- an **extension method** the import supplies: `values.Where(…)` keeps `import System.Linq` alive
  through the *declaring* type's namespace, with no LINQ type ever named;
- an **attribute**, in either CLR spelling: `[Obsolete("old")]` and `[ObsoleteAttribute("old")]` name
  one type, wherever the attribute sits — a function, a type, a member or a parameter;
- a name a namespace **declared but did not export**: the import supplied it and accessibility
  refused it, which is [NL308](./NL308.md)'s business and not this rule's.

Anything inside a `test` block is ordinary code and is read the same way.

## The rule has no list of names in it, and that is the point

It used to. NL010 answered from a hand-written table of the names each of ten well-known namespaces
provides — 112 spellings for `System` alone — read as a closed world. Both halves of that were wrong
in ways that shipped:

- **A gap in a row was a false positive on an error whose fix deletes code.** `import System` beside
  `OperatingSystem.IsWindows()` was reported unused, because the row had never heard of
  `OperatingSystem`, and `nlc fix` offered to delete the import the build needs. The row could never
  be finished: the namespace has thousands of public types and grows every release.
- **A namespace with no row was never reported at all.** A dead `import System.Runtime.CompilerServices`
  — or a dead import of your own project's namespace — was invisible, so the rule was silent exactly
  where your own code is.

Neither is possible now. A namespace that supplied nothing is reported whatever its name is, and a
namespace that supplied one thing is used.

## It is answered by the analysis, so a file that was not analysed is not judged

An import's use is a binding fact, and a file that was never bound has none. `nlc check`, `nlc build`,
`nlc test`, `nlc fix`, `nlc query` and the language server all analyse before they lint, so all of
them report the rule. A caller that only parsed a file gets silence rather than a guess — NL010 is an
error whose fix deletes a line, and guessing is what the table did.

A file whose own analysis reported nothing is judged; a file whose analysis did not run to completion
is not.

## An aliased import is used by BOTH of the things it does

`import System.Text as Txt` is not C#'s `using Txt = System.Text;`. C#'s alias binds the alias and
nothing else, so `new StringBuilder()` under it does not compile. N#'s form does both jobs at once:
it binds `Txt` **and** brings the namespace's own names into scope unqualified. This file builds:

```n#
import System.Text as Txt

class Report {
    builder: System.Text.StringBuilder = new StringBuilder()

    func Size(): int {
        return builder.Length
    }
}
```

So both spellings are uses of the SAME import and both credit the same namespace as the name
resolves: the alias-qualified `Txt.StringBuilder` is expanded to `System.Text.StringBuilder` before
the arithmetic runs, and the bare `StringBuilder` needs no expanding. Only a file that writes neither
is reported, and the span is the namespace rather than the alias.

## A fully qualified name does not use an import

Writing the whole path — `System.Text.StringBuilder`, `NSharpLang.Compiler.CodeIntelligence
.CompletionEngine` — resolves without any import at all, so an import whose namespace appears only in
fully qualified spellings really is dead and NL010 reports it. This is the same rule C# applies
(Roslyn's IDE0005 calls such a `using` unnecessary), and deleting the line is safe: the qualified
names keep resolving.

```n#
import System.Text          // ERROR NL010

class Report {
    builder: System.Text.StringBuilder = new System.Text.StringBuilder()

    func Size(): int {
        return builder.Length
    }
}
```

One bare mention anywhere in the file is enough to keep it, including a bare name written only in a
field initializer — those are read by the rule like any other body.

## The code fix reads this same answer

`nlc fix`'s "Remove unused import" is driven by this diagnostic and by nothing else, so `nlc fix`
loads the project and analyses it before it lints — the fixes it offers are the ones `nlc check`
reports, and never a strictly smaller set.

The end-to-end contracts live in `tests/native/census-import-usage`: every channel above is a file
whose ONLY mention of its import is that one position, and every reported import is paired with a
removal control that builds without it — so an NL010 is never asserted without proof that the import
really is dead.
