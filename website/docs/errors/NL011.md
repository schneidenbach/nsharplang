# NL011: an empty catch block

A `catch` block with no statements in it is an error. Catching an exception is a claim that you know
what to do about it; an empty block turns that claim into silence, and the failure it swallowed
reappears somewhere else as missing data, a wrong result, or nothing at all. N# makes you write
down the decision.

```n#
func ParseCount(text: string): int {
    try {
        return int.Parse(text)
    } catch (error: FormatException) {          // ERROR NL011
    }

    return 0
}
```

```text
── [NL011] ERROR ───────────────────────────── Program.nl:4:7 ──

    4 |     } catch (error: FormatException) {          // ERROR NL011
      |       ^^^^^

This catch block is empty — exceptions will be silently swallowed

Suggestion: Log it, handle it, return a fallback, or wrap it in a `throw new ...`. If ignoring it is deliberate, put `// nlc:ignore NL011` on the line above the `catch` — a comment alone does not clear this.
```

The span is the `catch` keyword rather than the brace, so the diagnostic points at the clause that
made the promise, not at the empty body that broke it.

## Why is this an error?

An empty catch is the only construct in common use whose entire purpose is to destroy information.
Everything else that goes wrong leaves a trace — a stack, a log line, a non-zero exit — and this one
guarantees there is none. The bug that follows is found by bisecting behaviour rather than by
reading a message, which is the most expensive way to find anything.

It is also nearly always accidental in the long run. Empty catches are written during debugging, to
get past an exception that was not the problem being chased, and then they ship. A build-blocking
rule is what separates "I am silencing this for the next ten minutes" from "this is how the code
handles failure".

## How to fix it

Handle it. Usually that means the operation had a non-throwing form all along:

```n#
func ParseCount(text: string): int {
    parsed := 0
    if int.TryParse(text, out parsed) {
        return parsed
    }

    return 0
}
```

Rethrowing, wrapping, logging, or returning a fallback all satisfy the rule. So does a single
statement that records the decision — the requirement is that *something* is written, not that it
be sophisticated.

## A comment is not enough

The rule counts *statements*, and a comment is not one — this file still reports NL011:

```n#
func ParseCount(text: string): int {
    try {
        return int.Parse(text)
    } catch (error: FormatException) {
        // not a number; zero is fine
    }

    return 0
}
```

The diagnostic used to suggest exactly that, which cost the reader an edit and then reported the same
error again; it now names only fixes that work, and points at the suppression for the deliberate
case. Where a comment really is the whole answer, pair it with `// nlc:ignore NL011` on the line
above the `catch`, so the decision is recorded in a form the compiler and the next reader both
understand:

```n#
func ParseCount(text: string): int {
    try {
        return int.Parse(text)
    // nlc:ignore NL011
    } catch (error: FormatException) {
    }

    return 0
}
```

## What silences it

- **Any statement at all** in the block, including a `throw new …` that wraps the caught exception
  and rethrows it. A bare `throw` is not an N# form — it does not parse — so wrapping is how you
  re-raise.
- **A `catch` that returns.** `catch (error: FormatException) { return -1 }` is a decision, and is
  never reported.
- The rule looks only at `catch` blocks. The general empty-block style rule that once covered the
  rest was retired and folded into `nlc format`, which produces no diagnostic at all.
