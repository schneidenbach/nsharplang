# NL414: the call is ambiguous

Two overloads accept this call and neither is better than the other, so there is no answer for the
compiler to give. N# will not break the tie by declaration order, by metadata order, or by any other
accident of how the candidates happened to reach it: the call means two different things, and only
you can say which.

```n#
namespace Example

class Picker {
    static func Pick(first: object, second: string): string {
        return second + first.ToString()
    }

    static func Pick(first: string, second: object): string {
        return first + second.ToString()
    }
}

func UsePicker(): string {
    return Picker.Pick("a", "b")          // ERROR NL414
}
```

```text
── [NL414] ERROR ───────────────────────────────── A.nl:14:19 ──

    14 |     return Picker.Pick("a", "b")          // ERROR NL414
       |                   ^^^^

The call to 'Pick' is ambiguous

The call to `Pick` is ambiguous — two overloads match it equally well:

Hint: Both of these match the arguments you wrote:
  - Pick(first: object, second: string): string
  - Pick(first: string, second: object): string

Neither is more specific than the other, so I will not choose one for you.
Say which you meant: cast an argument to the parameter type that overload declares, annotate a lambda's parameter types, or write the call's type arguments explicitly.

See: https://schneidenbach.github.io/nsharplang/docs/errors/NL414
```

The first overload is better for the *second* argument (`string` exactly, rather than `object`), the
second is better for the *first*. Neither wins every position, so neither wins the call.

## Why is this an error?

N# picks between applicable overloads with the same rule C# uses (ECMA-334 §12.6.4.3, "better
function member"): a candidate wins when, for **every** argument, its parameter is at least as good a
conversion target as the other candidate's, and for at least one argument it is strictly better.
"Better" means the argument's own type exactly, first; failing that, the more specific of the two
parameter types — the one that converts to the other and not back.

If neither candidate wins every position, the language has nothing more to say. Choosing anyway
would mean the meaning of your call depends on the order the overloads were declared in, or — for a
method read out of a referenced assembly — on the order the metadata reader happened to produce. Two
builds of the same program could disagree. N# reports the tie instead.

## How to fix it

### Cast an argument

Give one argument the exact type the overload you want declares:

```n#
namespace Example

func UsePicker(): string {
    label: object = "a"
    return Picker.Pick(label, "b")
}
```

### Annotate a lambda's parameters

When the tied position is a lambda, its own shape is what leaves the candidates tied. Writing the
parameter types names one delegate and rules the other candidate out:

```n#
namespace Example

func Fold(values: List<int>): int {
    return values.Aggregate((total: int, value: int) => total + value)
}
```

### Write the type arguments

A generic call whose type arguments are inferred can be closed by hand:

```n#
namespace Example

func Named(values: IEnumerable): List<string> {
    return values.Cast<string>().ToList()
}
```

## The method-group case

This is the most common way to meet NL414, and it is not about the argument types at all:

```n#
namespace Example

import System.Collections.Generic
import System.Linq

class Mapper {
    static func Describe(value: string): string {
        return value
    }

    static func Describe(value: string, index: int): string {
        return value + index.ToString()
    }
}

func UseMapper(items: List<string>): IEnumerable<string> {
    return items.Select(Mapper.Describe)          // ERROR NL414
}
```

`Enumerable.Select` declares two selector overloads — one taking `Func<TSource, TResult>` and one
taking `Func<TSource, int, TResult>`. The method group `Mapper.Describe` has an overload that fits
each, so both `Select` overloads apply, and `Func<string, string>` and `Func<string, int, string>`
are unrelated types: neither is a better conversion target. Pass a lambda that names the shape you
want, or give the two methods different names.
