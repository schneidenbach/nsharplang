# NL339: one type name declared in two files of one namespace

A namespace cannot contain two types with the same name and the same number of type parameters. On
the CLR a type's identity is its **full name** — namespace plus name plus arity — so two declarations
that agree on all three are one identity written twice, and an assembly carrying both has two
`TypeDef` rows under one name. Nothing can tell them apart: a reference to the name resolves to
whichever the loader reached first, and which one that is depends on emission order.

This is the cross-file half of [`NL306`](./NL306.md). NL306 is the same mistake made twice in one
file; NL339 is the same mistake split over two, which a per-file scope cannot see.

```n#
// FILE Catalog.nl
namespace Catalog

class Widget {
    Name: string => "first"
}
```

```n#
// FILE Program.nl
namespace Catalog

class Widget {            // ERROR NL339
    Label: string => "second"
}
```

```text
── [NL339] ERROR ────────────────────────────────── Program.nl:4:7 ──

    4 | class Widget {            // ERROR NL339
      |       ^^^^^^

A type named 'Widget' is already declared in this namespace, at Catalog.nl:4 — one namespace cannot
contain two types with the same name

Suggestion: Rename one of the two declarations, move one into a different namespace, or delete the
copy if 'Widget' was pasted into a second file by mistake.
```

The report lands on the **second** declaration and names where the first one is, so the two halves of
one collision are one diagnostic rather than two. Which declaration counts as "second" is decided by
the project's file order, not by the order the compiler happened to analyse them in, so the same
declaration is reported every run.

A file that only *uses* the name is not reported. `w := new Widget()` in a third file of `Catalog`
resolves to the first declaration the project enumerates, so the one NL339 is the whole report — the
use site does not add an [NL201](./NL201.md) "not found" for a type that exists twice. The compiler's
emitter refuses such a program on its own as well, so no path builds an assembly with two `TypeDef`
rows of one name.

A file that passes one declaration's `Widget` to a function written against the *other's* is a
different matter: the two are still two types, so that call is also a type mismatch
([NL202](./NL202.md)). Because the two share a name and a namespace, NL202 spells each with the
declaration it came from — `` Cannot pass `List<Widget [Catalog.nl:4]>` ... of type `List<Widget [Program.nl:4]>` `` —
so every one of those reports names the same two declarations this one does, and they all go away
with it.

The keyword plays no part — `class Widget` in one file and `struct Widget` in another are still one
identity — but the arity does: `Widget` beside `Widget<T>` is two types. And only files that compile
**together** share a namespace — the same rule [NL306](./NL306.md) applies to free functions, and the
two codes always agree. A `project.yml` says the files are one program, and so does a tool that
compiles them from a project of its own (the playground's files are one program). In a folder of
standalone scripts with no `project.yml`, each file is its own program, and two of them each
declaring `class Person` collide with nothing.

## How to fix it

**Rename one of them.** Two types that both wanted to be called `Widget` usually mean two different
things; giving each its own name is the fix that survives the next reader.

```n#
namespace Catalog

class WidgetPart {
    Label: string => "second"
}
```

**Or put one in its own namespace.** `Catalog.Widget` and `Catalog.Parts.Widget` are two identities
on the CLR and may coexist.

```n#
namespace Catalog.Parts

class Widget {
    Label: string => "second"
}
```

**Or delete the copy.** The most common cause is a file copied as a starting point whose type header
was never changed. If the two bodies are the same, one of them is dead code.

## When it does not fire

**Different type-parameter counts are different types.** `Widget` and `Widget<T>` are
`Widget` and `` Widget`1 `` in metadata, so they may sit in one namespace — in one file or across
two.

```n#
namespace Catalog

class Widget { }

class Widget<T> { }       // fine: a different arity is a different type
```

**Different namespaces are different scopes.** Two files that declare `Widget` under two namespaces
collide with nothing.
