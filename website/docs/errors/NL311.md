# NL311: a modifier this member cannot carry

`virtual`, `abstract` and `override` describe **slots** — places in a type's layout that a derived
type can fill. NL311 is the report for a member that carries one of those words but has no slot to
go with it: an `override` with nothing above it to override, or a bare `Name: T` member that is a
**field** — storage, which the CLR gives no slot.

```n#
class Counter {
    virtual count: int          // ERROR NL311
}
```

```text
── [NL311] ERROR ──────────────────────────── Program.nl:2:13 ──

    2 |     virtual count: int          // ERROR NL311
      |             ^^^^^

'count' is declared 'virtual', but a camelCase or 'private' member is the type's own storage — a field, which has no slot

Suggestion: Name it in PascalCase (or write 'protected' or 'public') so it is an auto-property that can be virtual, or drop 'virtual'.
```

The distinction the message is drawing is easy to miss on the way past. A bare member is one of two
CLR shapes, and N# picks it by one rule (see
[Fields and properties](../types.md#fields-and-properties)): an **exported instance member of a class
or record** is an auto-property, and everything else is a field. An auto-property's accessors are
methods, so `virtual Count: int` is C#'s `public virtual int Count { get; set; }` and is fine — it is
what EF Core's lazy-loading proxies override. `virtual count: int` is the class's own camelCase
storage, a field, and a field has no slot at all.

## Why is this an error?

Each of the three words is a claim about dispatch, and each one is either honoured by the runtime or
it is not. A field has no v-table entry, so `virtual` on one is a promise the metadata cannot carry.
An `override` with no base slot is the same kind of claim about a slot that does not exist. Left
alone, both would be quietly dropped and the access you expected to dispatch would bind statically
instead.

## How to fix it

Make the member an auto-property, and the word means what it says:

```n#
class Counter {
    virtual Count: int
}
```

Or drop the word, and keep the storage:

```n#
class Counter {
    count: int
}
```

## The sentences for a bare member

Each refusal names the rule that made the member storage, because the way out differs:

| The member | The report |
|------------|------------|
| `virtual count: int`, `private virtual Count: int` | a camelCase or `private` member is the type's own storage — a field, which has no slot |
| `static virtual Count: int` | a static member has no slot to dispatch through |
| `virtual readonly Count: int`, `virtual const Count: int` | a `readonly` / `const` member is a field, and a field has no slot |
| `virtual init Count: int` | an `init` member cannot be virtual, abstract or overridden — its declaring type writes the storage directly, which an override could not intercept |
| a member of a `struct` or `record struct` | a struct / record struct cannot take part in inheritance |
| a value member of an `interface` | an interface's value member is already a slot |
| `virtual Count: int` in a `sealed class` | the class is sealed |
| `abstract Count: int = 0` | an abstract property has no storage for an initializer to fill — give the value to the override |
| `abstract Count: int` outside an `abstract class` (or in a `record`) | only an abstract class can hold an abstract slot |
| `sealed Count: int` with no `override` | only an `override` can be sealed |

And for `override Name: T` over a base property:

- **no base property of that name** — `'Name' is declared 'override', but the base type has no
  property of that name`;
- **a base property that is not `virtual`, `abstract` or `override`** — mark the base `virtual`;
- **a base property with no setter** — a bare member overrides **both** accessors (C#'s CS0546), so a
  get-only base such as `Exception.Message` cannot be overridden this way. Override the getter alone
  with `override Message: string => …` ([a property written with accessors](#a-property-written-with-accessors)).

## `readonly` in front of something that is not a struct

The other family NL311 covers is the **type-level `readonly` modifier**. `readonly struct`,
`readonly ref struct` and `readonly record struct` all promise that no instance state changes
after construction — a promise only a value type can make, because it is what lets callers skip
defensive copies. A class, record, interface, enum, union, soa record or type alias cannot carry
the word:

```n#
readonly class Config {          // ERROR NL311
    Name: string = ""
}
```

```text
── [NL311] ERROR ───────────────────────────── Program.nl:1:1 ──

    1 | readonly class Config {          // ERROR NL311
      | ^^^^^^^^

'readonly' applies only to structs, but this declares a class

A 'readonly' type promises that none of its instance state can change after construction. Only
a struct — 'readonly struct', 'readonly ref struct' or 'readonly record struct' — can make that
promise; a class cannot.

Hint: Mark the individual members 'readonly' instead, or declare the type as a struct.
```

The squiggle is on the **word**, not on the type name, and the rest of the declaration keeps
parsing as though `readonly` had not been written — so a class that also has other problems
reports them instead of vanishing behind a syntax cascade. This mirrors C#'s `CS0106`.

To make a whole reference type immutable, mark its fields `readonly` one at a time; that is
what the word means on a class.

## The `override` faults, and their sentences

**A bare member with an inheritance modifier that is a field.** See
[the sentences for a bare member](#the-sentences-for-a-bare-member) above. `static`, `readonly` and
`required` on their own are untouched — they describe storage, not dispatch.

**`override` with no base member of that name.** Usually a typo or a member that moved:

```n#
class Greeter {
    override func Hello(): string {          // ERROR NL311
        return "hi"
    }
}
```

That reports `'Hello' is declared 'override', but it has no base member of that name`.

**`override` over a base member that is not overridable.** The base exists, but is not marked
`virtual`, `abstract`, or a non-`sealed` `override`:

```n#
class Animal {
    func Speak(): string {
        return "..."
    }
}

class Dog : Animal {
    override func Speak(): string {          // ERROR NL311
        return "woof"
    }
}
```

That reports `'Speak' is declared 'override', but it is not marked 'virtual', 'abstract' or
'override'`, and suggests marking the base member `virtual` — the fix is one level up, which is why
the message says so rather than just refusing the derived member.

## An event's four refusals

An event's accessors **are** methods, so `virtual`, `abstract` and `override` mean on an event what
they mean on a `func` and are accepted — see
[the tour](../language-tour.md#virtual-abstract-and-override). What NL311 refuses on an event is what
the CLR cannot carry, and each sentence names the one thing you can change:

```n#
import System

class Registry {
    static virtual event Registered: EventHandler   // ERROR NL311 — a static event has no slot
}

struct Gauge {
    virtual event Tripped: EventHandler             // ERROR NL311 — a struct is sealed
}

class Box {
    abstract event Changed: EventHandler            // ERROR NL311 — 'Box' is not an abstract class
}

sealed class Shut {
    virtual event Changed: EventHandler             // ERROR NL311 — 'Shut' is sealed
}

class Derived: Box {
    override event Missing: EventHandler            // ERROR NL311 — no base event of that name
}
```

The `override` verdicts are the same two the `func` family gets, over the same base chain: a base
event that is not marked `virtual`, `abstract` or `override` reports that it is shut, and no base
event of that name reports that it is absent.

## A property written with accessors

A property written with accessors — `Text: string => …` or `Count: int { get { … } set { … } }` — is
a pair of methods, so `virtual`, `override` and `sealed override` mean on it what they mean on a
`func`, on each accessor it declares (see
[Properties](../types.md#virtual-and-override-on-a-written-property)). NL311 refuses the same shapes
it refuses on a bare member, each with its own sentence:

```n#
class Label {
    sealed Text: string => "x"                 // ERROR NL311 — only an 'override' can be sealed
    static virtual Count: int => 0             // ERROR NL311 — a static property has no slot
}

struct Point {
    virtual Length: double => 0.0              // ERROR NL311 — a struct cannot take part in inheritance
}

sealed class Shut {
    virtual Text: string => "x"                // ERROR NL311 — 'Shut' is sealed
}
```

An `override` gets the `func` family's two verdicts — no base property of that name, or one that is
not `virtual`, `abstract` or `override` — and one of its own. **An override replaces each accessor it
declares, so a `set` needs a setter slot in the base** (C#'s CS0546):

```n#
import System

class ParseError: Exception {
    override Message: string {                 // ERROR NL311
        get { return "parse error" }
        set { }
    }
}
```

That reports `'Message' is declared 'override', but the base property has no setter to override`.
`Exception.Message` is get-only, so it is overridden with a getter alone —
`override Message: string => "parse error"`. Going the other way is fine: a get-only override of a
get/set base property replaces the getter and inherits the setter, as C#'s does. (Over an
**abstract** get/set property the inherited setter is still abstract, and a concrete class reports
[NL324](./NL324.md) for `Name.set`.)

## `abstract` on a member that has nowhere to be abstract

An `abstract` member is a **slot with no implementation**, and a slot needs somewhere to live. Two
different faults hide behind the one word, and each has its own sentence.

The first is an owner that cannot hold a slot. A concrete class carrying an abstract method is a
type the CLR refuses outright — before this rule the whole check ended in
`Type must be declared abstract if any of its methods are abstract.`, with no file, no line and no
column anywhere in the output:

```n#
class Widget {
    abstract func Touch()                // ERROR NL311 — 'Widget' is not an abstract class
}

sealed class Shut {
    abstract func Touch()                // ERROR NL311 — 'Shut' is sealed
}

struct Point {
    abstract func Touch()                // ERROR NL311 — a struct is sealed by the CLR
}

interface IWidget {
    abstract func Touch()                // ERROR NL311 — an interface's func is already a slot
}

abstract class Base {
    static abstract func Touch()         // ERROR NL311 — a static func has no slot to dispatch through
}
```

The second is a body. An abstract member supplies none — the emitter treats `abstract` as "this
member *is* its declaration" — so a body written beside the word was dropped in silence and the code
never ran:

```n#
abstract class Widget {
    abstract func Touch() {              // ERROR NL311 — an abstract func supplies no body
        print "hi"
    }
}
```

A **property with accessors** always has a body, so `abstract` on one is refused the same way. The
body-less spelling of a property is the bare member — `abstract Name: string` is C#'s
`public abstract string Name { get; set; }` — and the suggestion names it beside the two get-only
slots:

```n#
abstract class Widget {
    abstract Name: string { get { return "x" } }   // ERROR NL311
}

// The spellings that work:
abstract class Widget2 {
    abstract Name: string            // a get/set slot every concrete subclass overrides
}

abstract class Widget3 {
    abstract func Name(): string     // a get-only slot
}

interface IWidget3 {
    Name: string                     // a get-only slot
}
```

## An `override` that narrows the slot's accessibility

The CLR refuses to load a type whose override is **less accessible** than the slot it takes. The
program below compiled, verified, and then threw at the first call —
`System.TypeLoadException: … cannot reduce access.` — with no diagnostic anywhere in the build:

```n#
class Base {
    public virtual func Speak(): string {
        return "base"
    }
}

class Derived: Base {
    protected override func Speak(): string {     // ERROR NL311
        return "derived"
    }
}
```

```text
── [NL311] ERROR ─────────────────────────── Program.nl:8:29 ──

    8 |     protected override func Speak(): string {
      |                             ^^^^^

'Speak' is declared 'protected override', but the slot it takes is 'public' — an override cannot narrow the accessibility it inherits

Suggestion: Declare 'Speak' 'public' to match the slot, or leave the base member 'protected'. The CLR refuses to load a type whose override reduces access.
```

The message names the slot's accessibility because that is the fact the source in front of you does
not show — the word is on the **base** member, one file away.

Remember that N# reads an unannotated member's accessibility from its **casing**: a PascalCase member
is public, a camelCase one is assembly-private. So `protected override func Speak()` narrows a slot
that `func Speak()` opened, even though neither declaration writes `public`.

Only **narrowing** is reported. Widening an override — `public override` over a `protected` slot —
loads and runs, so N# leaves it alone: the arbiter here is the CLR, not C#'s stricter rule that the
two must match exactly.

### A `protected internal` slot in another assembly is worth `protected` here

`protected internal` is a **union**: the family half reaches every derived type, the assembly half
reaches only the assembly that declared the member. Across an assembly boundary the assembly half is
unreachable, so what your override inherits is the family half alone — plain `protected`.

```n#
import System.Linq.Expressions

// `ExpressionVisitor.VisitExtension` is `protected internal virtual` in System.Linq.Expressions.
class Marker: ExpressionVisitor {
    protected override func VisitExtension(node: Expression): Expression {   // fine
        return node
    }
}
```

`protected override` there is an exact match, not a narrowing, and it is emitted `family` — the same
metadata C#'s `protected override` produces for the same base. Writing `protected internal override`
instead is a **widening**: it adds the assembly half back on *your* side, which the CLR permits, so
N# honours the word and emits `famorassem`. (C# reports CS0507 for that spelling because C# requires
an exact match; N# follows the runtime, as it does for every other widening.)

Two things put the assembly half back:

- **`InternalsVisibleTo`.** If the declaring assembly names your compilation as a friend, its
  internals *are* reachable from your code, the union is whole again, and `protected override` over
  a `protected internal` slot is a narrowing once more — exactly as it is inside one assembly.
- **Being in the same assembly.** A source base in your own project keeps both halves, so the rule
  above does not apply to it at all.

`private protected` is an **intersection** (family *and* assembly), so the same boundary erases it
entirely: a member declared `private protected` in another assembly cannot be reached, let alone
overridden, from outside that assembly unless it granted you a friend declaration.

## Silence is the default

The walk answers only over shapes it can actually read: a source base class, a CLR type it can
reflect over, or the implicit `object` at the end of a source chain. A base clause that did not
resolve reports nothing at all — a modifier verdict computed from half a chain is not a verdict.

Two consequences you will meet in ordinary code:

- `override func ToString()` on a class with **no `:` clause** is silent. The class inherits
  `object`, `object.ToString` is virtual, and the override takes its slot.
- `override func GetType()` is an error, because `object.GetType` is not virtual.

The same care is taken for properties, and it is why these two lines behave differently on a
`class MyError : Exception`:

```n#
override Message: string => "boom"          // fine — Exception.Message is virtual
override HResult: int => 1                  // ERROR NL311 — Exception.HResult is not
```
