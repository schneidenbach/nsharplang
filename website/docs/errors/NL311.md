# NL311: a modifier this member cannot carry

`virtual`, `abstract` and `override` describe **slots** — places in a type's layout that a derived
type can fill. NL311 is the report for a member that carries one of those words but has no slot to
go with it: an `override` with nothing above it to override, or a field, which the CLR gives no slot
at all.

```n#
class Label {
    virtual Text: string          // ERROR NL311
}
```

```text
── [NL311] ERROR ──────────────────────────── Program.nl:2:13 ──

    2 |     virtual Text: string          // ERROR NL311
      |             ^^^^

'Text' is declared 'virtual', but a field cannot be virtual, abstract or overridden

Suggestion: Give it an accessor — 'Text: <type> => <expression>' or a 'get'/'set' block — so it becomes a property, or drop 'virtual'.
```

The distinction the message is drawing is easy to miss on the way past. N# decides field-versus-property
from what follows the **type**, never from the modifiers. `virtual Text: string` has no accessor, so
it is a field, and the emitted metadata makes it a CLR field — which cannot be virtual, abstract or
overridden by anything.

## Why is this an error?

Each of the three words is a claim about dispatch, and each one is either honoured by the runtime or
it is not. A field has no v-table entry, so `virtual` on a field is a promise the metadata cannot
carry. An `override` with no base slot is the same kind of claim about a slot that does not exist.
Left alone, both would be quietly dropped and the call you expected to dispatch would bind
statically instead.

## How to fix it

Give the member an accessor, and it becomes a property — properties do have slots, so `virtual`
means something:

```n#
class Label {
    virtual Text: string => ""
}
```

Or drop the word, and keep the field:

```n#
class Label {
    Text: string = ""
}
```

## The three faults, and their three sentences

**A field with an inheritance modifier.** `virtual`, `abstract` and `override` are all refused, each
naming the word you wrote: `'Text' is declared 'abstract', but a field cannot be virtual, abstract or
overridden`. `static`, `readonly` and `required` are untouched — they describe storage, not dispatch.

**`override` with no base member of that name.** Usually a typo or a member that moved:

```n#
class Greeter {
    override func Hello(): string {          // ERROR NL311
        return "hi"
    }
}
```

That reports `'Hello' is declared 'override', but it has no base member of that name`.

**`override` over a base member that is not overridable.** The base exists, but is not marked
`virtual`, `abstract`, or a non-`sealed` `override`:

```n#
class Animal {
    func Speak(): string {
        return "..."
    }
}

class Dog : Animal {
    override func Speak(): string {          // ERROR NL311
        return "woof"
    }
}
```

That reports `'Speak' is declared 'override', but it is not marked 'virtual', 'abstract' or
'override'`, and suggests marking the base member `virtual` — the fix is one level up, which is why
the message says so rather than just refusing the derived member.

## Silence is the default

The walk answers only over shapes it can actually read: a source base class, a CLR type it can
reflect over, or the implicit `object` at the end of a source chain. A base clause that did not
resolve reports nothing at all — a modifier verdict computed from half a chain is not a verdict.

Two consequences you will meet in ordinary code:

- `override func ToString()` on a class with **no `:` clause** is silent. The class inherits
  `object`, `object.ToString` is virtual, and the override takes its slot.
- `override func GetType()` is an error, because `object.GetType` is not virtual.

The same care is taken for properties, and it is why these two lines behave differently on a
`class MyError : Exception`:

```n#
override Message: string => "boom"          // fine — Exception.Message is virtual
override HResult: int => 1                  // ERROR NL311 — Exception.HResult is not
```
