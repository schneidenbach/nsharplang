# NL326: a mutable instance field in a readonly struct

A `readonly struct` promises that **none of its instance state changes after construction**.
NL326 is the report for an instance field inside such a type that was left writable, which is
the one thing that promise cannot survive.

```n#
readonly struct Point {
    X: int                      // ERROR NL326
    readonly Y: int

    constructor(x: int, y: int) {
        X = x
        Y = y
    }
}
```

```text
── [NL326] ERROR ───────────────────────────── Program.nl:2:5 ──

    2 |     X: int                      // ERROR NL326
      |     ^

'X' is a mutable instance field, but 'Point' is a readonly struct

Suggestion: Declare the field 'readonly X: <type>' so it can only be assigned in a
constructor, or drop 'readonly' from 'readonly struct Point' if the value is meant to change
after construction.
```

## Why is this an error?

`readonly struct` is not a comment. The compiler puts
`System.Runtime.CompilerServices.IsReadOnlyAttribute` on the emitted type, and every consumer
that reads that attribute — N#, C#, F# and the CLR's own rules for `in` parameters — *stops
making the defensive copies* it would otherwise make when the value is reached through a
readonly location.

So a writable field in a `readonly struct` is worse than a broken promise. Consider a method
that takes the value by `in` and assigns a field: without the attribute the callee mutates a
copy and the caller sees nothing; with the attribute there is no copy, and the write lands on
the caller's value. The rule closes that gap at the declaration, where it is one word to fix,
rather than at the call site, where it is invisible.

This is the same rule C# enforces as `CS8340`.

## How to fix it

Add the word, if the field really is set once during construction:

```n#
readonly struct Point {
    readonly X: int
    readonly Y: int

    constructor(x: int, y: int) {
        X = x
        Y = y
    }
}
```

Or drop `readonly` from the type, if the value is meant to change:

```n#
struct Point {
    X: int
    Y: int
}
```

A plain `struct` with `readonly` fields is **not** the same thing and is never reported here —
it stays a mutable struct that happens to have some immutable fields, and it carries no
`IsReadOnlyAttribute`.

## What the rule does not cover

- **`static` and `const` fields.** They belong to the type, not to any value of it, so they
  are not instance state and a `readonly struct` may declare them freely.
- **`init` fields.** `init` storage is written once during construction, which is exactly what
  the type promises. (C# accepts an init-only auto-property in a readonly struct for the same
  reason.)
- **Properties.** A computed member (`Area: double => Width * Height`) holds no state. A
  property with a hand-written `set` is allowed too — if its body tries to write a field, that
  field is `readonly` and the write is [NL309](./NL309.md)'s business.
- **`readonly ref struct` and `readonly record struct`** are held to the same rule as
  `readonly struct`, because all three carry the same promise.
