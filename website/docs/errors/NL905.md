# NL905: a value that may be null is used without a guard

N# tracks, statement by statement, whether each value can be null at the point you use it. NL905 is
what it says when a path reaches a dereference, a call or an index while the compiler still believes
the value might be absent.

```n#
class Box {
    Width: int
}

func Read(box: Box?): int {
    return box.Width          // ERROR NL905
}
```

```text
── [NL905] ERROR ──────────────────────────── Program.nl:6:12 ──

    6 |     return box.Width          // ERROR NL905
      |            ^^^

Possible null dereference: `box` is maybe-null

Suggestion: Use '?.', add a '??' fallback, guard with 'if box == null { return }', or explicitly assert after proving 'box' is not null.
```

Two things in that message are worth reading carefully. The backtick-quoted `box` is the **path** N#
is tracking, and it appears again in every suggestion — the diagnostic is about that specific path,
not about the type. And `maybe-null` is a flow state rather than a declaration: it is what the
compiler knows *here*, which is why the same expression can be fine three lines later.

## Why is this an error?

The alternative is `NullReferenceException`, found by a user. N# embraces .NET's nulls rather than
pretending they do not exist, which means the type `Box?` is a real and useful thing to write — and
the price of that is that the compiler insists you deal with the `null` half before dereferencing.

## How to fix it

Narrow the value. An early return is the plainest way, and the narrowing holds for the rest of the
function:

```n#
class Box {
    Width: int
}

func Read(box: Box?): int {
    if box == null {
        return 0
    }

    return box.Width
}
```

Once the `null` branch has left the function, `box` is known to be present on every remaining path
and the access is silent.

## The three operations

NL905 names which operation it caught, and the wording changes with it:

| What you wrote | Operation | Message |
|---|---|---|
| `box.Width` | dereference | `Possible null dereference` |
| `box.Width()` | call | `Possible null call` |
| `values[0]` where `values` is `int[]?` | index | `Possible null index` |

The suggestions differ too: the dereference case offers `?.`, the index case offers `?[`, and the
call case offers `?.` on the member.

## What clears the state

Anything that proves the value is present on this path:

- a comparison against `null` whose failing branch leaves — `if box == null { return }`;
- a `??` fallback, which supplies a value for the absent case;
- `must`, which unwraps explicitly and says so;
- assigning a value the compiler already knows is non-null.

A **null-conditional** access is silent by construction rather than by narrowing: `box?.Width` never
reports NL905, because `?.` *is* the guard. Note that the current backend does not yet lower every
null-conditional shape and may answer [NL103](./NL103.md) where the analyzer is happy — that is a
code-generator gap, not a second opinion about nullability.

## What N# tracks, and what it does not

Only a **stable path** carries a fact: a local, a parameter, or a chain of plain member reads off
one. Assigning to any prefix of a path invalidates everything derived from it, so rewriting `a.b`
forgets what was known about `a.b.c`.

Reports are deduplicated on the position, the path *and* the operation together. A chain that
dereferences two different maybe-null values at the same position therefore reports twice — those
are two distinct mistakes that happen to share a column.
