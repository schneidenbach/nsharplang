# NL016: a null check on something just created

A `null` comparison against an expression that was just constructed is an error. `new StringBuilder()`
and `[1, 2]` cannot be null — the operator that produced them either yields an object or throws — so
the comparison has one answer before the program runs, and the branch it guards either always runs
or never does.

```n#
import System.Text

func BuildLabel(): string {
    builder := new StringBuilder()
    if new StringBuilder() != null {          // ERROR NL016
        builder.Append("ready")
    }

    return builder.ToString()
}
```

```text
── [NL016] ERROR ───────────────────────────── Program.nl:5:8 ──

    5 |     if new StringBuilder() != null {          // ERROR NL016
      |        ^^^

This null check is redundant — the expression was just created and can never be null (this is always true)

Suggestion: Remove the null check — the value cannot be null
```

The message names the constant the comparison folds to. `!= null` on something freshly created is
*always true*; `== null` on the same expression is *always false*, and the diagnostic says which one
you wrote.

## Why is this an error?

This shape almost never starts life this way. It is what a refactor leaves behind when the operand
used to be a lookup that could fail — `cache.Find(key) != null` becomes `new Entry() != null` when
the lookup is replaced by construction, and the guard reads as if it still protects something. The
branch underneath is now dead code that looks live, which is the expensive kind.

The second reason is that the two readings of "is this null" are not equally harmless. An
always-false `== null` silently skips its body; an always-true `!= null` silently runs it. Neither
failure announces itself at run time, so the compile is the only place to catch it.

## How to fix it

Drop the comparison and keep the work:

```n#
import System.Text

func BuildLabel(): string {
    builder := new StringBuilder()
    builder.Append("ready")
    return builder.ToString()
}
```

If the branch was protecting against a *failure* rather than a null, the fix is to restore whatever
can actually fail — a lookup, a parse, a nullable field — not to keep a check that cannot fire.

## What counts as freshly created

Two shapes, and only two:

- a **`new` expression**, of any type: `new StringBuilder()`, `new int[3]`;
- an **array literal**: `[1, 2]`.

Which side `null` sits on does not matter — `null == new int[3]` is reported the same as
`new int[3] == null`.

Everything else is silent. A variable that *holds* a freshly created object is not reported — the
rule reads the expression written in the comparison, not where the value came from, and a variable
can be reassigned between the two lines. A
value-type literal on the other side is [NL003](./NL003.md) instead — the two rules read the same
comparison shape and partition it, so exactly one of them can ever fire on a given check.
