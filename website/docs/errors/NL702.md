# NL702: two imports bring in the same name

An unaliased file import places everything the imported file exports directly into your file's
scope. When two of them export the same name, that name has two meanings and N# will not pick one
for you. NL702 is reported once per colliding name, at the **second** import — the one that made
the name ambiguous.

Here are two small libraries, each of which exports a function called `Format`:

```n#
// lib/text.nl
func Format(value: int): string {
    return $"{value}"
}
```

```n#
// lib/money.nl
func Format(value: int): string {
    return $"${value}"
}
```

and a file that imports both:

```n#
// FILE text.nl
namespace Lib.Text

func Format(value: int): string {
    return value.ToString()
}
```

```n#
// FILE money.nl
namespace Lib.Money

func Format(value: int): string {
    return "$" + value.ToString()
}
```

```n#
import "./text.nl"
import "./money.nl"          // ERROR NL702

func Describe(value: int): string {
    return Format(value)
}
```

Read the hint rather than the underline: it lists **every** import the colliding name came from, so
you can see which two definitions are in conflict without opening either file.

```text
── [NL702] ERROR ───────────────────────────── Program.nl:2:8 ──

    2 | import "./money.nl"          // ERROR NL702
      |        ^^^^^^^^^^^^

Imported symbol 'Format' is defined by multiple file imports

The symbol 'Format' is imported more than once, so N# cannot choose which definition to use.

Hint: N# found 'Format' in these file imports: "./text.nl", "./money.nl".
Unaliased file imports place their exported symbols directly in scope. An alias on one import silences this, but a call through an alias (`Alias.Format(...)`) is not yet lowered — renaming one declaration is the fix that builds.

Suggestion: Rename one of the two 'Format' declarations so each name means one thing — an alias clears the collision but an alias-qualified CALL does not compile yet.
```

## Why is this an error?

`Format(value)` in that file has two candidate definitions and no rule that prefers one. N# could
have picked the last import and moved on — that is what a scope built by overwriting does — but the
resulting program would silently call a different function the moment you reordered your imports.
A name whose meaning depends on line order is not a name.

## How to fix it

**The fix depends on what collided, and the diagnostic says which.** A colliding TYPE is told to
alias; a colliding FUNCTION is told to rename. The reason is the backend, and it is measured rather
than assumed — see the caveat below.

For two functions, rename one of them:

```n#
// FILE money.nl
namespace Lib.Money

func FormatMoney(value: int): string {
    return "$" + value.ToString()
}
```

```n#
import "./text.nl"
import "./money.nl"

func Describe(value: int): string {
    return Format(value)
}

func DescribePrice(value: int): string {
    return FormatMoney(value)
}
```

For two types, alias one import. An aliased import fills its own table and puts nothing in the
unqualified scope, so the collision disappears and each `Tag` gets an unambiguous spelling:

```n#
import "./text.nl"
import "./money.nl" as Money

func MakeText(name: string): Tag {
    return new Tag(name)
}

func MakeMoney(code: string): Money.Tag {
    return new Money.Tag(code)
}
```

## What does and does not collide

**Only unaliased file imports contribute.** An import that already carries `as` is invisible to
this check — you can alias two files that both export `Format` and nothing is reported.

**Only exported declarations contribute.** A name that the imported file does not export is not in
your scope and cannot collide with anything.

**Namespace imports are a separate mechanism.** `import System` and `import System.Text` do not
participate: NL702 is about the quoted-path form.

**The report is per name, not per import.** Two files that share three exported names produce three
NL702 diagnostics, each naming its own symbol, all pointing at the same second import line.

## Why the two arms differ

The alias always clears NL702 — `nlc check` reports nothing about the import after the change. What
differs is whether the aliased symbol is still reachable, and that was measured on the shipped
compiler:

| spelling | result |
|---|---|
| `Money.Tag` as a type, and `new Money.Tag(...)` | compiles |
| `Money.Format(value)` — a call through the alias | [NL103](./NL103.md) `emit.call.static-member-unmodeled` |
| `Lib.Money.Format(value)` — fully qualified | [NL301](./NL301.md) `Variable 'Lib' not found` |
| renaming one of the two declarations | compiles |

So aliasing a colliding **type** leaves you with two usable names, and aliasing a colliding
**function** leaves you with one usable name and one you cannot call. That is why the diagnostic
sends the two cases different ways, and why it no longer tells everyone to alias.
