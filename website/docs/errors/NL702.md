# NL702: two imports bring in the same name

An unaliased file import places everything the imported file exports directly into your file's
scope. When two of them export the same name, that name has two meanings and N# will not pick one
for you. NL702 is reported once per colliding name, at the **second** import — the one that made
the name ambiguous.

Here are two small libraries, each of which exports a function called `Format`:

```n#
// lib/text.nl
func Format(value: int): string {
    return $"{value}"
}
```

```n#
// lib/money.nl
func Format(value: int): string {
    return $"${value}"
}
```

and a file that imports both:

```n#
import "../lib/text.nl"
import "../lib/money.nl"          // ERROR NL702

func Describe(value: int): string {
    return Format(value)
}
```

Read the hint rather than the underline: it lists **every** import the colliding name came from, so
you can see which two definitions are in conflict without opening either file.

```text
── [NL702] ERROR ───────────────────────────── Program.nl:2:8 ──

    2 | import "../lib/money.nl"          // ERROR NL702
      |        ^^^^^^^^^^^^^^^^^

Imported symbol 'Format' is defined by multiple file imports

The symbol 'Format' is imported more than once, so N# cannot choose which definition to use.

Hint: N# found 'Format' in these file imports: "../lib/text.nl", "../lib/money.nl".
Unaliased file imports place their exported symbols directly in scope. Use an alias on one import to make the reference explicit.

Suggestion: Add an alias to one import, such as `import "../lib/money.nl" as Alias`, and qualify the symbol.
```

## Why is this an error?

`Format(value)` in that file has two candidate definitions and no rule that prefers one. N# could
have picked the last import and moved on — that is what a scope built by overwriting does — but the
resulting program would silently call a different function the moment you reordered your imports.
A name whose meaning depends on line order is not a name.

## How to fix it

Alias one of the imports. An aliased import fills its own table and puts nothing in the unqualified
scope, so the collision disappears and each `Format` gets an unambiguous spelling:

```n#
import "./lib/text.nl"
import "./lib/money.nl" as Money

func Describe(value: int): string {
    return Format(value)
}

func DescribePrice(value: int): string {
    return Money.Format(value)
}
```

Renaming one of the two exports works just as well, and is the better move when you own both files
and the two names were never meant to be the same word.

## What does and does not collide

**Only unaliased file imports contribute.** An import that already carries `as` is invisible to
this check — you can alias two files that both export `Format` and nothing is reported.

**Only exported declarations contribute.** A name that the imported file does not export is not in
your scope and cannot collide with anything.

**Namespace imports are a separate mechanism.** `import System` and `import System.Text` do not
participate: NL702 is about the quoted-path form.

**The report is per name, not per import.** Two files that share three exported names produce three
NL702 diagnostics, each naming its own symbol, all pointing at the same second import line.

## A caveat about the aliased form

The alias clears NL702 — verified: `nlc check` reports nothing about the import after the change.
The **backend** is a step behind the analyzer here, and a qualified call through an import alias
(`Money.Format(value)`) currently stops at [NL103](./NL103.md) with
`emit.call.static-member-unmodeled`. If you hit that, renaming one of the two exports is the fix
that compiles today.
