# NL109: reserved keyword used as a name

N# has eighty-five reserved words, and a name is not one of them. This is a distinct code from
[NL101](./NL101.md) on purpose: the token is not surplus and nothing is missing — the fix is always
to rename.

```n#
class Greeter {
    Name: string

    func Rename(text: string) {
        Name = text.union          // ERROR NL109
    }
}
```

```text
── [NL109] ERROR ──────────────────────────── Program.nl:5:21 ──

    5 |         Name = text.union          // ERROR NL109
      |                     ^^^^^

Expected member name. Got the reserved keyword 'union'

'union' is a reserved keyword in N#, so it can't be used as a name here.

Hint: After a member access, the name must not be a reserved keyword. To reach a  member literally named 'union', access it through a differently-named alias.

Suggestion: Rename it to 'unionValue' or '_union'
```

The suggestion is part of the diagnostic. N# proposes both conventions it accepts, so the fix is a
copy rather than a decision.

## Why is this an error?

`union`, `record`, `match`, `type`, `file`, `base`, `params` and the rest are how N# tells one
construct from another. A name that collides with one makes the surrounding code ambiguous to the
parser, and — because the parser cannot recover cleanly — it often takes the whole enclosing
declaration with it.

## How to fix it

Rename, at every use:

```n#
class Greeter {
    Name: string

    func Rename(text: string) {
        Name = text.unionValue
    }
}
```

## The words that surprise people

Several reserved words read like ordinary nouns, and these are the ones that actually cost people
time: `type`, `record`, `union`, `file`, `match`, `base`, `params`, `on`, `must`, `throws`,
`scoped`, `required`, `alloc`, `allow`, `partial`, `newtype`, `nameof`.

Three that look reserved and are **not**: `test`, `field` and `property` are ordinary names.

## Where the position lands

When the keyword is a parameter or local name, recovery is imperfect: the compiler may report the
position at the enclosing declaration and follow it with errors about code that is fine. If you see
a cluster of errors around a declaration and one NL109 in it, fix the NL109 first — the rest are
usually consequences.
