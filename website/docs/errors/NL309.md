# NL309: a readonly field is assigned outside its constructor

`readonly` means the field is written once, while the object is being built, and never again. NL309
is a write that happens somewhere else. The exemption is narrow on purpose: it covers the
constructor's own body and the field's initializer, and nothing else.

```n#
class Counter {
    readonly Id: int

    constructor(id: int) {
        Id = id
    }

    func Reset() {
        Id = 0          // ERROR NL309
    }
}
```

```text
── [NL309] ERROR ───────────────────────────── Program.nl:9:9 ──

    9 |         Id = 0          // ERROR NL309
      |         ^^

Field 'Id' is readonly — it can only be assigned in a constructor

Suggestion: Move this assignment into a constructor, or remove `readonly` if the field needs to change later.
```

The squiggle is on the assigned field name, so a qualified write — `this.Id = 0` — underlines `Id`
too, not `this`.

## Why is this an error?

A `readonly` field is a promise to every reader of the type that the value they saw at construction
is the value they will see later. Code leans on that: it caches the field, it hashes on it, it hands
it out without defensive copying. A write from an ordinary method breaks the promise silently, so
N# refuses the write rather than the reasoning.

## How to fix it

If the value belongs to construction, set it there — one write, in the constructor:

```n#
class Counter {
    readonly Id: int

    constructor(id: int) {
        Id = id
    }

    func Describe(): string {
        return "counter " + Id.ToString()
    }
}
```

If the field genuinely needs to change during the object's life, then it is not readonly. Drop the
modifier rather than working around it:

```n#
class Counter {
    Id: int

    constructor(id: int) {
        Id = id
    }

    func Reset() {
        Id = 0
    }
}
```

## The cases people get wrong

**The constructor exemption does not follow you into a nested body.** A lambda written inside the
constructor is a separate body that runs later — possibly much later — so a write to a readonly
field from inside it is NL309:

```n#
import System

class Counter {
    readonly Id: int
    Reset: Action

    constructor(id: int) {
        Id = id
        Reset = () => {
            Id = 0          // ERROR NL309
        }
    }
}
```

**Structs and records are covered by the same rule.** A bare-name write inside a `struct` method —
no `this.` in front of it — is still a write to the field:

```n#
struct Point {
    readonly X: int

    constructor(x: int) {
        X = x
    }

    func Zero() {
        X = 0          // ERROR NL309
    }
}
```

**Every way of writing counts.** Compound assignment is a write, so `Id += 1` reports NL309. So does
an **object initializer**, which looks like construction but is not the constructor —
`new Counter { Id: 5 }` runs after the object exists, and reports NL309 on `Id`. Passing the field
as a `ref` or `out` argument is a write the callee would make, and gets its own sentence:
`Fill(out Id)` reports `Field 'Id' is readonly — it can't be used as a out argument`.

**`static readonly` is stricter still, and says so.** A static readonly field can only be
initialized at its declaration — not in a static method, and not in a constructor — so its message
is a different sentence: `Field 'Name' is static readonly — it can only be initialized at its
declaration`.

## The same code on a `using` resource

NL309 also covers the one **local** that is read-only: a `using` statement's resource. The statement
promises to release whatever the name holds when its region ends, and it can only keep that promise
while the name is still holding it — so rebinding the name is either a leak (the first resource is
never released) or a double release, and neither is what the author meant.

```n#
import System.IO

func Run(path: string) {
    using reader := new StreamReader(path) {
        reader = new StreamReader(path)      // ERROR NL309
    }
}
```

```text
── [NL309] ERROR ───────────────────────────── Program.nl:5:9 ──

    5 |         reader = new StreamReader(path)      // ERROR NL309
      |         ^^^^^^

The using resource 'reader' is read-only — it can't be assigned with '='

Suggestion: A `using` disposes whatever this name holds when its region ends, so the name has to
keep holding it. Bind the new value to a different name, or give it its own `using`.
```

The rule follows the binding's **region**, not the statement: a `using` BLOCK's resource is read-only
inside the block, and a using DECLARATION's is read-only for the rest of the enclosing block —
exactly as long as each is visible. Writing **through** the resource (`reader.Position = 0`) is
ordinary mutation and stays legal; only rebinding the name is refused.

## An `in` parameter written to

The third producer, and the one whose promise reaches outside your own code. An
[`in` parameter](../functions.md#in-parameters) passes the CALLER's storage by reference and declares —
in metadata, with `[IsReadOnlyAttribute]`, which every C# and F# consumer reads — that the callee will
not write to it. Writing through it would break that for the caller, silently and at a distance, so
each of these is NL309:

```n#
struct Matrix {
    A: double
}

func Measure(in m: Matrix): double {
    m.A = 1.0          // ERROR NL309
    return m.A
}
```

The other three writes report the same code with their own sentence: assigning the parameter itself
(`m = new Matrix { A: 1.0 }`), changing a member with `++`, and passing the parameter on as a `ref` or
an `out` argument — which is the ESCAPE, and the one that would otherwise let the next callee write
what this one promised not to.

The fix is one of two things. If the callee genuinely needs its own value, **copy it into a local**
first — a copy is yours to change and costs one struct copy, which is what a by-value parameter would
have cost anyway. If the callee is meant to change what the caller passed, the parameter was declared
wrongly: make it `ref`, which says so.

Reading is unrestricted: arithmetic, comparisons, member reads, and passing it on as a by-value or a
further `in` argument are all fine.
