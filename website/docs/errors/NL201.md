# NL201: a written type name resolves to nothing

A type annotation has to name a type that exists. NL201 is what N# reports when a name written
in a type position resolves to nothing — no declaration in this project, no imported namespace
that supplies it, no referenced assembly. The compiler stops there rather than inventing a
placeholder and reporting the consequences instead of the cause.

```n#
class Order {
    Customer: Buyer          // ERROR NL201
    Total: int
}
```

```text
── [NL201] ERROR ──────────────────────────── Program.nl:2:15 ──

    2 |     Customer: Buyer          // ERROR NL201
      |               ^^^^^

Type 'Buyer' not found

Suggestion: Check the spelling, add the missing 'import', or add the package/project reference that provides 'Buyer'.
```

The caret covers the name and nothing else, and the suggestion lists the three things that can
actually be wrong: the spelling, a missing `import`, or a missing package or project reference.

## Why is this an error?

Every later question the compiler asks about `Customer` — how wide the field is, what members it
has, whether a value can be stored in it — needs the type. There is no useful answer to give
once the name is unresolved, so continuing would mean guessing, and each guess would produce
its own diagnostic pointing somewhere other than the actual mistake.

## How to fix it

Declare the type, import the namespace that has it, or fix the spelling. Here the type simply
did not exist yet:

```n#
class Buyer {
    Id: int
}

class Order {
    Customer: Buyer
    Total: int
}
```

## Every position that reports NL201

NL201 fires anywhere a type is *written*, and the whole set behaves the same way:

- a field type — `Customer: Buyer`;
- a parameter type — `func Read(b: Buyer)`;
- a return type — `func Read(): Buyer`;
- a base class or an interface in a base list — `class Order : Buyer`;
- the type after `new` — `new Buyer()`;
- the **head** of a generic — `Bag<int>` reports one NL201 on `Bag`, with the caret on the three
  letters of the head, not on the argument list.

An unresolved **return** type is the one position that draws a second report. The return check
still runs against the name it could not resolve, so `func Read(): Buyer` followed by any
`return` also produces an [NL202](./NL202.md) reading *should return Buyer but returns ...*.
Fix the NL201 and the second report goes with it.

## Three things that are not NL201

**A name in an expression position.** `Buyer.Count` in the middle of an expression is read as a
variable, not as a type, and reports [NL301](./NL301.md) — undefined variable. The distinction
is the position, not the name: the same word is NL201 after a `:` and NL301 before a `.` in an
expression.

**A real BCL type you forgot to import.** `Builder: StringBuilder` does not report NL201. The
linter recognises the name and reports `NL002` instead, with the exact import to add:

```text
'StringBuilder' is used without the import that provides it

Suggestion: Add 'import System.Text' at the top of the file
```

NL201 does not also fire on that line — the missing-import report is the whole diagnostic.

**A dotted name.** A qualified type reference such as `Sales.Buyer` is not resolved by this
check at all. If nothing supplies it, the failure surfaces later as an [NL103](./NL103.md)
decline from the backend naming the field it could not resolve, rather than as an NL201 on the
annotation.
