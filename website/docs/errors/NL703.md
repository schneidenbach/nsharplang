# NL703: imports form a cycle

File imports have to flow in one direction. When a file imports itself, or imports a file that
imports it back, there is no order in which the two can be resolved — each needs the other's symbols
to already be in scope. N# reports the cycle at the import line that closes it.

The shortest cycle has length one: a file that imports itself.

```n#
import "./Program.nl"          // ERROR NL703

func Greet(name: string): string {
    return "hello " + name
}

func Shout(name: string): string {
    return Greet(name).ToUpper()
}
```

The message spells the cycle out as a path, and repeats it in the hint. That path is what to read —
it names every file involved, in the order the imports connect them.

```text
── [NL703] ERROR ───────────────────────────── Program.nl:1:8 ──

    1 | import "./Program.nl"          // ERROR NL703
      |        ^^^^^^^^^^^^^^

Circular import detected: Program.nl -> Program.nl

File imports form a cycle: Program.nl -> Program.nl

Hint: Circular imports are not allowed because they make symbol resolution order ambiguous.
Import path: Program.nl -> Program.nl

Suggestion: Move shared types or functions into a separate file/package that every file can import without importing back, or invert one dependency so imports flow in one direction.
```

## Why is this an error?

Resolving a file import means parsing the imported file and pulling its exported declarations into
your scope. To do that for a cycle, N# would have to already know what each file exports before it
has finished reading either — and where that is possible at all, the answer depends on which file
the compiler happened to start from. A build whose symbol resolution changes with file ordering is
not reproducible, so N# refuses the cycle rather than picking an order.

## How to fix it

Break the cycle by giving the shared code a file of its own that both sides can import without
importing back:

```n#
// lib/naming.nl
func Decorate(name: string): string {
    return "<" + name + ">"
}
```

```n#
// Program.nl
import "./lib/naming.nl"

func Greet(name: string): string {
    return Decorate("hello " + name)
}
```

When the shared code genuinely belongs to one side, the other fix is to invert the dependency: move
the function that reaches backwards into the file it reaches into.

## Cycles longer than one file

The realistic version of this mistake is two files that import each other, and it produces one
diagnostic naming both:

```text
Circular import detected: Helper.nl -> Program.nl -> Helper.nl
```

Longer chains are found too. Three files where `A` imports `B`, `B` imports `A`, and `Program.nl`
imports `A` report the cycle once, at the import that closes it, as
`A.nl -> B.nl -> A.nl` — the two files that actually form the loop, not every file that leads into
it.

**The cycle is reported once, not once per file.** Each participant repeating the same complaint
would turn one mistake into N diagnostics that all describe the same loop.
