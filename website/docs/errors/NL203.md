# NL203: an expression with no type to infer from

`:=` takes the variable's type from the value on its right. A few expressions have no type of
their own — they are written to be *told* what to produce — and putting one on the right of a
`:=` leaves nothing to infer from. NL203 is that: not a mismatch, but the absence of any
expected type to work with.

```n#
class Person {
    Name: string
}

func Make(): Person {
    p := new()          // ERROR NL203
    return p
}
```

```text
── [NL203] ERROR ──────────────────────────── Program.nl:6:10 ──

    6 |     p := new()          // ERROR NL203
      |          ^^^

I can't figure out what type 'new()' should create here — add a type annotation or write the type after 'new'

Suggestion: For example, use `value: Person = new()` when the target type is clear, or `new Person()` when it is not.
```

The caret sits on `new()`, not on `p`. The variable is not the problem; the expression is, and
the suggestion offers both directions out of it.

## Why is this an error?

`new()` means "construct whatever this position expects". In `p: Person = new()` the annotation
supplies that expectation; after a `:=` nothing does. N# infers a local's type from its
initializer and from nothing else — not from the enclosing function's return type, not from how
the variable is used later — so a `:=` whose right-hand side is itself waiting to be told a
type has no answer to give, and guessing one would make the local's type depend on edits made
somewhere else in the file.

## How to fix it

Either annotate the variable and keep the target-typed `new()`:

```n#
class Person {
    Name: string
}

func Make(): Person {
    p: Person = new()
    return p
}
```

or name the type after `new` and keep the `:=`:

```n#
class Person {
    Name: string
}

func Make(): Person {
    p := new Person()
    return p
}
```

Both compile. Which reads better depends on whether the type is more informative on the left or
on the right.

## The shapes with no type of their own

**`new()`** — the target-typed constructor, above.

**A lambda with untyped parameters.** A lambda is not a value with a type; it is a value that
*takes* the shape of the delegate type it is assigned to. Bare on the right of `:=` there is no
delegate type, and each parameter is reported by name:

```text
I can't figure out the type of lambda parameter 'x' — nothing here names the lambda's delegate type

Suggestion: Give the lambda a typed home (e.g., 'let f: Func<int, int> = x => ...') or pass it
directly where a delegate type is expected.
```

Naming the delegate type fixes it, and `Func` resolves without an import:

```n#
func Go(): int {
    f: Func<int, int> = x => x + 1
    return f(1)
}
```

Passing the lambda straight into a parameter that has a delegate type works for the same
reason: the parameter supplies the expectation the `:=` did not.

**`default`.** `value := default` reports NL203 as well. Note that the annotated form the
message suggests does not currently compile either — `value: int = default` is refused by the
front end with an [NL103](./NL103.md) parse decline — so `default` is not usable in N# today by
either spelling. Write the value you mean (`0`, `null`, `new T()`) instead.

## What NL203 is not

NL203 fires when there is **no** expected type. When there is one and the value disagrees with
it, that is [NL202](./NL202.md) — including the case where the expected type is a bare type
parameter such as `A` or `T`. And when the expression *does* have a type but the name in the
annotation does not exist, that is [NL201](./NL201.md), reported on the annotation rather than
on the value.
