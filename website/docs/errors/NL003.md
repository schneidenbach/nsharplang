# NL003: a null check on a value-type literal

A comparison against `null` whose other side is a value-type literal is an error. `3 == null` is not
a question — `int` has no null, so the comparison has one answer before the program runs, and the
branch it guards is either dead or the guard is not the one you meant to write. N# reports the
condition rather than folding it away.

```n#
func RetryBudget(): int {
    if 3 == null {          // ERROR NL003
        return 0
    }

    return 3
}
```

```text
── [NL003] ERROR ───────────────────────────── Program.nl:2:8 ──

    2 |     if 3 == null {          // ERROR NL003
      |        ^

This null check is unnecessary — 'int' is a value type and can never be null

Suggestion: You can safely remove this null check
```

The caret sits on the operand, not on the whole comparison: the literal is what makes the check
pointless, so that is what the diagnostic points at.

## Why is this an error?

A null check that cannot fail is a check somebody wrote for a reason. Usually the reason has moved:
the operand used to be a nullable field, a refactor replaced it with a literal default, and the
guard survived intact. Reporting it makes the refactor finish. Silently accepting it leaves a
condition that reads like a safety check and is not one — and a reader who trusts it will not add
the check that is actually missing.

The rule knows exactly four literal kinds — `int`, `float`, `char` and `bool` — and has no
catch-all case underneath them, so it never guesses that some other expression is a value type.

## How to fix it

Delete the check and keep the branch you actually wanted:

```n#
func RetryBudget(): int {
    return 3
}
```

## When N# stays quiet

- **A string literal is not a value type.** `"s" == null` is a legal, meaningful comparison and NL003
  says nothing about it.
- **A variable of a value type is not this rule.** NL003 reads the *literal* on the other side of
  the `null`, so `count != null` where `count: int` draws nothing from it. The mistake is still
  caught — that program stops at the backend with an [NL103](./NL103.md) decline on the comparison —
  but not here, and not with this message.
- **Which side `null` is on does not matter**, and neither does `==` versus `!=`. `null == 3` is
  reported the same way, with the caret moved to the literal.
- **A `new` expression or an array literal is the other rule.** `new Widget() != null` is
  [NL016](./NL016.md); the two partition the same shape and never both fire on one comparison.

Each comparison is reported on its own. A function with three of them gets three NL003s, one per
line.
