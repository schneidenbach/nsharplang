# NL306: a name is declared twice in the same scope

Within one scope, a name means one thing. NL306 is the report for a second declaration of a name
that scope already has — a repeated field, two locals, two parameters, or two top-level functions in
the same file.

```n#
func Area(w: int): int {
    return w * w
}

func Area(w: int): int {          // ERROR NL306
    return w + w
}
```

```text
── [NL306] ERROR ───────────────────────────── Program.nl:5:6 ──

    5 | func Area(w: int): int {          // ERROR NL306
      |      ^^^^

'Area' is already declared in this scope — each name must be unique within the same scope
```

The span is on the **name**, on the second declaration. The first one is left alone: it is the one
the rest of the file has been reading, and moving the report to it would point at working code.

## Why is this an error?

Every use of the name after the second declaration would have to pick a winner, and any rule for
picking one is a rule the reader has to know before they can read the function. N# does not have
such a rule and does not want one — Go's answer, and N#'s, is that the ambiguity is the bug.

## How to fix it

Give the second declaration its own name:

```n#
func Area(w: int): int {
    return w * w
}

func Perimeter(w: int): int {
    return w + w
}
```

## The scopes this is asked in

The rule follows scopes rather than syntax, so it covers more than top-level functions:

```n#
class Point {
    X: int = 0
    X: int = 0          // ERROR NL306
}
```

```n#
func Go(): int {
    count := 1
    count := 2          // ERROR NL306
    return count
}
```

```n#
func Go(a: int, a: int): int {          // ERROR NL306
    return a
}
```

A duplicated **parameter** reports NL306 as well: N# has no separate duplicate-parameter code, and
the reason two parameters cannot share a name is the reason two locals cannot.

## What is not a duplicate

- **Reassignment.** `count = 2` is not a declaration and is never NL306. Only `:=`, `let` and a
  declaration form introduce a name.
- **Sibling scopes.** Two blocks that each declare `count`, neither nested in the other, are two
  scopes and two names.
- **Nested scopes.** An inner declaration that hides an outer one is not a duplicate — it is
  *shadowing*, which N# also rejects, under `NL316`. The distinction is worth keeping because the
  fixes differ: a duplicate is usually a copy-paste, and a shadow is usually a name that wanted to
  be more specific.

## A type's name includes its type-parameter count

A type is identified by its name **and** how many type parameters it declares, so two type
declarations collide only when both are the same. A non-generic type and a generic one of the same
name are two different types — that is the ordinary way to give a generic type a non-generic root —
and neither is NL306:

```n#
class Subscription {
}

class Subscription<T>: Subscription {          // fine: a different type-parameter count
}

class Subscription<T, U> {                     // also fine
}
```

What *is* NL306 is a repeated (name, type-parameter count), whatever keyword each declaration uses,
because the CLR has one type table rather than one per keyword:

```n#
class Shape<T> {
}

struct Shape<U> {          // ERROR NL306
}
```

```text
── [NL306] ERROR ───────────────────────────── Program.nl:5:8 ──

    5 | struct Shape<U> {          // ERROR NL306
      |        ^^^^^

A type named 'Shape<T>' already exists — a type name and its type-parameter count together must be unique

Suggestion: 'Shape' is also declared with 1 type parameter(s), which is allowed — two declarations
may share a name only when their type-parameter counts differ. Rename this one, or give it a
different type-parameter count.
```

The message names the type-parameter count whenever the file also declares that name at another
count, because "a type named 'Shape'" would otherwise be ambiguous in exactly the file where the
distinction matters.

Writing a type-parameter count that no declaration has is a different error —
[NL207](./NL207.md) — and it names the counts that do exist.
