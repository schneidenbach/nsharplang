# NL903: a name with no readable visibility

N# has no `public` or `private` keyword in ordinary use: **PascalCase means exported, camelCase means
package-private**, and the first character of a name is what says which. NL903 is what the compiler
reports when that first character is neither — a name it cannot classify has no visibility a reader
can see.

```n#
func _Compute(): int {          // ERROR NL903
    return 1
}
```

```text
── [NL903] ERROR ───────────────────────────── Program.nl:1:1 ──

    1 | func _Compute(): int {          // ERROR NL903
      | ^^^^^^^^

Identifier '_Compute' starts with a non-letter character — in N#, PascalCase means public and camelCase means private

Suggestion: Use PascalCase for public members or camelCase for private members
```

Note the severity. Despite the rule being a convention, this is a build-blocking error like almost
everything else in N#; the language is near-zero-warnings by policy.

## Why is this an error?

Visibility in N# is carried by the spelling, so the spelling has to answer the question. `_Compute`
starts with an underscore: it is not PascalCase, so it is not exported, and it is not camelCase, so
it is not deliberately package-private either. Every reader of that declaration — and every tool
that has to decide whether the name belongs in a package's public surface — is left guessing. N#
would rather you pick.

## How to fix it

Choose the visibility you meant, and spell it:

```n#
func computeTotal(): int {
    return 1
}

func ComputeAll(): int {
    return computeTotal()
}
```

`computeTotal` is visible inside the package and invisible outside it. `ComputeAll` is part of the
package's public API. Nothing else in the declaration changes.

## What NL903 does *not* complain about

This is the point people get wrong most often. NL903 fires **only** on a first character that is
neither an uppercase nor a lowercase letter. It is not a style checker:

- a camelCase public-looking API is not reported — it is simply package-private, which is a decision,
  not a mistake;
- a PascalCase helper you meant to keep internal is not reported — it is exported, and again that is
  a decision;
- `HTTP_Client`, `Two_Words` and other unconventional spellings are not reported, because their
  first character is a letter and that is the whole test.

Formatting is `nlc format`'s job and produces no diagnostics at all. NL903 exists for exactly one
thing: a name with no readable visibility.

## The four questions, in order

The check asks them in this order, and the order is the behaviour:

1. **Is the name empty?** Then there is no convention question.
2. **Does the declaration carry an explicit visibility modifier?** Then the modifier answers, and the
   spelling is never consulted. `private class _Cache` is accepted.
3. **Is the first character an uppercase letter?** Exported; done.
4. **Is the first character a lowercase letter?** Package-private; done.

Both tests look at `name[0]` and nothing else, which is why `HTTP_Client` and `Two_Words` are
accepted: the convention is about the first character, not about the shape of the whole name. The
lowercase test is `char.IsLower` and nothing weaker — it accepts an accented lowercase letter and the
eszett, and refuses the title-case and modifier letters an "is a letter and is not uppercase"
approximation would let through.

## Where it is asked

Ten declaration sites run the check: `class`, `struct`, `record`, `interface`, `union`, `enum` and
field declarations, plus top-level functions, local functions and properties. Two do not: an indexer
has no name to classify, and a `soa record` is not asked.
