# NL208: a type argument violates the type parameter's constraint

A `where` clause is a promise the generic's body relies on. NL208 is what N# reports when a type
argument breaks that promise: the count is right — that would be [NL207](./NL207.md) — and the
argument is a real type, but it is not a type the constraint admits. The message names the
offending argument, the type parameter, the owner, and the constraint, in that order.

```n#
class Wrapper<T> where T: struct {
    Value: T
}

func Make(): Wrapper<string> {
    return new Wrapper<string> { Value: "hi" }          // ERROR NL208
}
```

```text
── [NL208] ERROR ──────────────────────────── Program.nl:6:16 ──

    6 |     return new Wrapper<string> { Value: "hi" }          // ERROR NL208
      |                ^^^^^^^

`string` is not a non-nullable value type, but type parameter `T` of `Wrapper` requires one (the `struct` constraint)

Suggestion: Use a non-nullable value type for `T`, or relax the `struct` constraint on `Wrapper`.
```

Note where the caret lands: on `Wrapper` at the `new` site, not on the `Wrapper<string>` written
in the return type one line above. The constraint is checked when the type is *constructed*.

## Why is this an error?

`where T: struct` is a promise that every `Wrapper<T>` holds a value type: `Value` is never
null, and assigning it copies rather than aliases. `string` is a reference type, so neither
holds, and the body of `Wrapper` was written on the assumption that they do. Checking at the
point of substitution is what makes the promise worth anything — a constraint a caller can
violate is not a constraint, it is a comment.

## How to fix it

Pass an argument the constraint admits, or relax the constraint. Here `int` satisfies `struct`:

```n#
class Wrapper<T> where T: struct {
    Value: T
}

func Make(): Wrapper<int> {
    return new Wrapper<int> { Value: 7 }
}
```

The other direction — deleting `where T: struct` — is right when the body never actually needed
it. Read the body before deciding: a constraint added defensively is worth removing, and one the
body depends on is not.

## The constraints, and what each one says when it is broken

Each kind of constraint prints its own sentence, and each ends with a suggestion offering both
the fix at the use site and the fix at the declaration:

```text
`string` is not a non-nullable value type, but type parameter `T` of `Wrapper` requires one (the `struct` constraint)
`int` is a value type, but type parameter `T` of `Wrapper` requires a reference type (the `class` constraint)
`Blob` does not implement `IComparable`, which type parameter `T` of `Sorted` requires
```

The third form covers every constraint that names a type. It is the one that most often turns
out to be an oversight in the *argument* rather than in the constraint — implementing the
interface on `Blob` is usually the fix, not loosening `Sorted`.

## Where the check runs

**At a construction.** `new Wrapper<string> { ... }` is the shape in the example above.

**At a call.** A generic function's constraints are checked against the arguments inferred at
each call site, and the report lands on the call, naming the function:

```text
`string` is not a non-nullable value type, but type parameter `T` of `Biggest` requires one (the `struct` constraint)

Suggestion: Pass a non-nullable value type for `T`, or relax the `struct` constraint on `Biggest`.
```

**On the declaration itself, for a cycle.** A `where` clause set in which a type parameter is
constrained to itself — directly, or the long way round through its siblings — is reported once
on the declaration, no matter how many cycles it contains:

```text
Type parameter `T` of `Pick` has a circular constraint dependency

Suggestion: Remove the cycle in the `where` clauses of `Pick` — a type parameter cannot be
constrained to itself, directly or through other type parameters.
```

## A declared type alone is not checked

Writing `Wrapper<string>` as a field type, a parameter type or a return type, without ever
constructing one, currently reports nothing. This compiles clean today, constraint violation and
all:

```n#
class Wrapper<T> where T: struct {
    Value: T
}

class Holder {
    W: Wrapper<string>          // no NL208 here
    Count: int
}
```

So an NL208 can appear the first time you write `new`, on a type argument that has been sitting
in your signatures for a while. Where the diagnostic points is not necessarily where the mistake
was made — check the annotations that named the same argument.
