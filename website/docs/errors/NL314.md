# NL314: a result used before its error was checked

`result, err := f()` is N#'s error-capture form: it calls a function that can throw and hands you
two names — the value, and the exception that stopped it. Only one of the two is real on any given
run. Reading `result` before `err` has been checked is reading a value that may never have been
produced, so N# reports NL314 at the read.

```n#
import System

func Divide(a: int, b: int): int {
    if b == 0 {
        throw new Exception("cannot divide by zero")
    }

    return a / b
}

func Describe(a: int, b: int): string {
    result, err := Divide(a, b)
    doubled := result * 2          // ERROR NL314
    if err != null {
        return "failed"
    }

    return $"{doubled}"
}
```

The underline is on the **use** of `result`, not on the line that declared it. The declaration was
fine; the read is what happens too early.

```text
── [NL314] ERROR ─────────────────────────── Program.nl:13:16 ──

    13 |     doubled := result * 2          // ERROR NL314
       |                ^^^^^^

Result 'result' may be unavailable because 'err' can be non-null

Suggestion: Use 'result' only after `if err == null`, or return/throw from an `if err != null` error branch before the result is used.
```

## Why is this an error?

`result, err := Divide(a, b)` is not a tuple destructuring — it is a call whose exception was caught
for you. When `Divide` throws, the exception lands in `err` and `result` is whatever the failed call
left behind. Nothing in the value itself says "this is not an answer": an `int` that was never
computed looks exactly like an `int` that was.

That is exactly the failure mode this form exists to prevent. Go's `v, err :=` earns its safety from
the convention that everyone checks `err` first; N# makes the compiler check instead, so a forgotten
guard is a build error rather than a division that silently used zero.

## How to fix it

Check the error first and leave before touching the result:

```n#
import System

func Divide(a: int, b: int): int {
    if b == 0 {
        throw new Exception("cannot divide by zero")
    }

    return a / b
}

func Describe(a: int, b: int): string {
    result, err := Divide(a, b)
    if err != null {
        return "failed"
    }

    doubled := result * 2
    return $"{doubled}"
}
```

Either direction of the guard works. `if err == null { ... }` makes the result available **inside**
the branch, which is the shape to reach for when the success path is the short one:

```n#
func Describe(a: int, b: int): string {
    result, err := Divide(a, b)
    if err == null {
        return $"{result * 2}"
    }

    return "failed"
}
```

## The second name must be spelled `err`

The error-capture form is recognised by shape, not by the type of the call: **exactly two names,
and the second one literally `err`**. `error`, `Err` and `e` do not make one.

This matters more than it looks, because a near-miss is not "the same thing without the check" — it
is an ordinary tuple deconstruction, and it fails immediately against a function that does not
return a tuple:

```n#
result, error := Divide(a, b)      // NL103: Tuple deconstruction needs a tuple value,
                                   //        but this initializer is 'int'
```

So a misspelled `err` never silently loses you the guard. You get a different, louder error.
