# NL322: a member written through a temporary copy

Assigning to a member requires a receiver that is real storage. When the receiver is a value type
produced by a call — an indexer result, a property, a method's return value — you are holding a
*copy*, and the store would land in that copy and vanish with it. N# rejects the write instead of
compiling one that does nothing.

```n#
import System.Collections.Generic

struct Point {
    X: int
    Y: int
}

func Shift(points: List<Point>) {
    points[0].X = 5          // ERROR NL322
}
```

Read the "Actual" line and the hint together: the underline is on the receiver expression, and the
hint names why that particular receiver is a copy.

```text
── [NL322] ERROR ──────────────────────────── Program.nl:9:11 ──

    9 |     points[0].X = 5          // ERROR NL322
      |           ^^

Cannot assign to 'X' because its receiver is a temporary copy of 'Point', not a variable

This assignment writes through an indexer result (a copy of the element), but `Point` is a value type:

  Actual: `Point`

Hint: A value type is copied every time it is returned from a call, an indexer, or a
property. This write would land in that temporary copy and be thrown away with it —
the original value would never change.

Suggestion: Copy the value into a local first, modify the local, then store the whole value back (e.g. `tmp := …` / `tmp.X = …` / store `tmp`)
```

## Why is this an error?

`List<Point>`'s indexer is a method. It returns a `Point`, and because `Point` is a struct, it
returns a *copy* of the element — not a reference to the slot inside the list. `points[0].X = 5`
therefore mutates a temporary that is discarded on the next line. The list is unchanged, the code
looks correct, and nothing at run time reports anything.

This is C#'s CS1612, and it is one of the most reliably confusing errors in .NET precisely because
the failing version is *silent* if the compiler lets it through. N# takes the same position: a write
that provably cannot be observed is a compile error.

## How to fix it

Copy the value out, change the copy, and store it back. The three steps are explicit, and each one
does what it looks like:

```n#
import System.Collections.Generic

struct Point {
    X: int
    Y: int
}

func Shift(points: List<Point>) {
    p := points[0]
    p.X = 5
    points[0] = p
}
```

If a type is routinely mutated in place through a collection, that is also a signal that it may want
to be a `class` rather than a `struct` — a reference-typed element hands out the object itself, and
the original write would have worked.

## Which receivers are storage

**These count as storage, and NL322 does not report a write through them:**

- a local or parameter, and any field chain over one — `p.X = 5` where `p` is a local `Point`;
- `this`, and a bare field of `this`;
- an array element.

**These are copies, and writing through them is NL322:**

- an indexer result, as above;
- a **property** result — `b.Origin.X = 5` where `Origin` is a `Point`-valued property is the same
  mistake with a different spelling;
- any other call result.

Compound assignment counts as a write. `points[0].X += 1` is reported exactly as `= 5` is.

## Where the rule deliberately stays quiet

**Reference types are never affected.** A receiver of class type is a handle to storage no matter
what expression produced it, so every shape is assignable through it and NL322 has nothing to say.

**Unresolvable receivers are not guessed at.** If a hop in the receiver chain has a type or member
the analyzer cannot resolve here — an open generic, an external type it could not open — the rule
declines rather than reporting. NL322 is a claim that the write is provably lost; where the proof is
missing, so is the diagnostic.
